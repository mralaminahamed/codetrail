## What the automated floor does *not* cover

axe-core's `color-contrast` rule **cannot run under jsdom**: jsdom does not lay
out or composite, so `getComputedStyle` cannot resolve what a colour is drawn
against. The console's contrast is therefore **zero-covered** by the automated
suite — not partially covered — which is why pass 5 exists and was run in a real
browser.

## The five passes

### 1. Keyboard-only traversal of every view — PASS

Measured on `/repos` and on the repository page, reading the real tab order out
of the DOM:

```
tab order: [Skip to content, codetrail, Home, Corpus, <content links…>]
firstIsSkipLink: true
positiveTabIndexes: []
mainIsProgrammaticOnly: true   (main has tabindex="-1")
h1Count: 1
landmarks: { main: 1, nav: 1, header: 1 }
imagesWithoutAlt: 0
```

The skip link is the first focusable element and reaches `#main`. No element
carries a positive `tabindex` (`jsx-a11y/tabindex-no-positive` also refuses one
at lint time). Every form control resolves a `<label for>`.

Focus after a direct submission was checked live in the browser, not only in
jsdom: asking a question left `document.activeElement` on the result region
(`DIV` with `tabindex="-1"`).

### 2. A screen reader over submit → watch → ask — **NOT PERFORMED**

No screen reader was available in this environment. This is the pass most likely
to find what the other four miss — announcement order, double announcements, a
live region that re-reads on every poll — and it has **not** been done.

What stands in for it, and what that is worth: the live region's text is a pure
function of `status` with no counter, timestamp or elapsed time in it, and that
property is asserted by driving ten polls with an unchanged status and comparing
the region's `textContent` before and after (`Job.test.tsx`). That proves the
region does not re-announce on every poll. It does not prove the announcements
are in a sensible order or that the reading is pleasant. **Open, and it should
be run before anyone calls this console accessible.**

### 3. `prefers-reduced-motion` — PASS, vacuously

```
prefersReducedMotionSupported: true
elementsWithMotion: 0
runningAnimations: 0
```

The console has no transitions and no animations at all, so there is nothing for
the media query to reduce. Recorded as vacuous rather than as a pass, because
the first animation anyone adds makes this pass meaningful and it will need
re-running.

### 4. 200% zoom and 320px reflow — **ONE FINDING, FIXED**

At a 320 px viewport, **before** the fix:

```
viewport: 320    scrollWidth: 3409    bodyScrollsHorizontally: true
overflowingCount: 22
  CODE "dfd11cca1143ba03ba0fc0ff14e5dbb4d61f6f0a"  right: 384
  CODE "f1367cf168a232801012ee7ad8143bf5f1d9aa12…"  right: 615
  CODE "git show dfd11cca…| head -c -1 | sha256sum" right: 999
```

That is a WCAG 2.2 **1.4.10 Reflow** failure: content requiring two-dimensional
scrolling at 320 px. The cause is this product's own subject matter — 40-char
commit SHAs, 64-char digests and the `git show … | sha256sum` command are single
unbreakable tokens, and there are several per citation.

Fixed in `src/index.css`: `pre` gets `overflow-x: auto; max-width: 100%`, so a
code block scrolls inside its own box; an inline `code` and the tuple's `dd` get
`overflow-wrap: anywhere`, because a horizontal scrollbar per digest is worse
than a wrapped digest and copy-paste is unaffected by where it wraps.

**After** the fix, same viewport, same page, after asking a question:

```
viewport: 320    scrollWidth: 320    bodyScrollsHorizontally: false
overflowingCount: 5   — all of them <code> INSIDE a <pre>
preBlocksScrollThemselves: true
```

The body no longer scrolls horizontally; the five remaining wide elements scroll
inside their own container, which is the intended behaviour.

Closed by `src/reflow.test.ts`. That test asserts the **stylesheet's text**, not
the rendering, and it says so in the file: jsdom does not lay out, so no test in
this suite can measure a reflow. What it guards is silent deletion of the rules
this measurement added. The measurement above is the evidence; the test is the
ratchet.

Screenshot: `assets/screenshots/console-reflow-320.png`.

### 5. Colour contrast by hand, on every state — PASS

Computed in the browser from resolved RGB (the palette is authored in `oklch`,
which a naive parser reads as ratio 1.0 — the first run of this script produced
exactly that false positive and was corrected to resolve colours through a
canvas before measuring).

| Element | Foreground | Background | Ratio | Needs | |
| --- | --- | --- | --- | --- | --- |
| Skip link, focused | `rgb(21,27,36)` | `rgb(250,252,254)` | **16.82** | 4.5 | PASS |
| Skip link border | `rgb(21,27,36)` | `rgb(250,252,254)` | **16.82** | 3.0 | PASS |
| Body text, headings, links, code | `rgb(0,0,0)` | `rgb(255,255,255)` | **21.0** | 4.5 | PASS |

The skip link is off-screen until focused, so it was measured **focused** — the
only state in which its contrast can matter.

No state in this console signals anything by colour alone: provenance is the
word `resolved` or `syntactic`, staleness carries the word `superseded`, and a
refusal is distinguished from an error by role, heading and content rather than
by hue. That is asserted in the suite (`Callers.test.tsx`, `Staleness.test.tsx`)
as well as looked at here.

## Also observed, not a11y findings

- **Zero console errors or warnings** across the whole browser walk.
- Three `@theme` tokens — `--color-rule`, `--color-quiet`, `--color-alarm` —
  resolve to empty at runtime. Tailwind v4 emits only the custom properties a
  stylesheet actually uses, and nothing uses these three. Dead tokens in
  `index.css`; harmless, and removed rather than left to look load-bearing.

## Addendum, 2026-09-06 — the sweep's subject was replaced

Everything above measured a console with **one `className` in the whole `src/`
tree** and four hand-written CSS rules, importing Tailwind's preflight and
opting nothing back in. That is no longer what ships, so this section says which
of the five passes the design change invalidated and which it did not, rather
than leaving a dated file to read as though it still described the build.

| Pass | Still valid? |
| --- | --- |
| 1. Keyboard-only traversal | **Structurally, yes; not re-measured.** The skip link, `main[tabindex="-1"]`, the single `h1` and the absence of any positive `tabindex` are asserted in the suite (`Shell.test.tsx`, `routes.test.tsx`) and none of them moved. What did move: the header and nav are now one flex row, which changes their painted order, not their DOM order — the tab sequence is unchanged. |
| 2. Screen reader | **Still not performed, and now there is more to perform.** The answered path did not previously announce at all (focus was moved to an empty, unnamed div before React had rendered); it now moves in an effect keyed on the result, into a named `role="region"`. That is the fix, and **nothing here has heard it**. A refusal additionally sits inside that region as its own `role="status"`, so a double announcement is possible and unmeasured. |
| 3. `prefers-reduced-motion` | **Still vacuous, and deliberately kept that way.** The design adds no `transition`, no `animation` and no `@keyframes`; the pending state is a line of text rather than a spinner, for exactly this reason. `elementsWithMotion` should still be 0. |
| 4. 200% zoom / 320px reflow | **Rules kept, rendering not re-measured.** `pre { overflow-x: auto; max-width: 100% }`, `:not(pre) > code { overflow-wrap: anywhere }` and `dd { overflow-wrap: anywhere }` all survive and are still ratcheted by `src/reflow.test.ts`. New surfaces the 320px measurement has **not** seen: the citation card's two-column `dl` grid (whose first column is `minmax(5.5rem, max-content)`), the `.bar` flex row, and the `<details>` the check command now sits in. |
| 5. Colour contrast by hand | **Void.** It measured black on white. The palette is entirely new and has a dark theme, which did not exist. |

Pass 5 is replaced, in part, by `src/contrast.test.ts`: it reads the hex tokens
out of `src/index.css` and computes WCAG 2.x contrast for every pair the design
draws, in both themes — 4.5:1 for text, 3:1 for the two things WCAG 1.4.11
actually covers (a control's boundary and the focus ring). That is a stronger
guard than the hand measurement in one way and weaker in another, and both
halves matter:

- **Stronger:** it runs on every commit, it covers the dark theme, and a palette
  edit that drops a pair fails CI instead of shipping.
- **Weaker, and this is the honest half:** it asserts that a *named pair* clears
  a threshold. It does not know which token ends up behind which text, because
  nothing in jsdom lays out. A rule that put `--quiet` on `--code-bg` in a place
  the table does not list would still be uncovered. Decorative edges — a card
  border, a hairline — are deliberately **absent** from the table: 1.4.11 does
  not cover them, and claiming 3:1 for a hairline would be inventing a pass.

So: contrast is now covered *by construction of the palette* and still not
covered *as rendered*. A browser re-run of passes 1, 4 and 5 against the new
design, and pass 2 for the first time, is open.
