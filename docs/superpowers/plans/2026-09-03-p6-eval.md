**Goal:** Make the project's deferred claims measurable, and then measure them. Every phase since P2 has ended a paragraph with "P6 decides". This phase builds `apps/evalrunner`, generates a golden set mechanically from doc comments, indexes the doc-comment-stripped corpus twice — once per chunking arm, at one commit — runs the *shipped* retriever over both, and reports hit@k, MRR and refusal behaviour in both directions. It then calibrates the score floor from the resulting distribution of **the vector arm's cosine similarity** — the quantity `rag.Decide` actually compares — records the numbers that produced it in a committed artefact, and states what would invalidate it. CI runs the same harness on `embed.Fake` as a mechanics check, and every artefact that run produces says, in its first field and in its filename, that its figures are not quality.

**Architecture:** Four internal packages under `apps/evalrunner/internal`, because none of them is shared and spec §2 closes `packages/shared`'s list (spec:45–46). `golden` derives cases from raw source and resolves each case's answer range **against the stripped source**, which is the subtlest thing in the phase and the one P2 wrote a test comment specifically to warn P6 about. `metric` is pure arithmetic — hit@k, reciprocal rank, mean, and the four-cell refusal confusion — with every assertion on a hand-computed value. `corpus` is the contract between the two arms: same commit, same file bytes, different span sets, different databases, and a leakage probe that **refuses to run** rather than reporting a number nobody can trust. `cmd` runs one retrieval pass per case per arm, records everything, and sweeps the floor offline from what it recorded. Two small changes land in shipped code: one refusal rule with two callers, and a decision about `vectorSearchSQL`'s missing tie-break.

**Tech Stack:** Go 1.27, Postgres 17 + pgvector via the `pgvector/pgvector:pg17` image — **a floating tag, not a pinned one**; see Global Constraints — `go/ast` + `go/parser` + `go/token`, `encoding/json`. **No new dependency.** Nothing in this phase reaches the network except the `git clone` the existing indexer already does.

**Spec:** `docs/superpowers/specs/2026-08-31-codetrail-design.md` — **§9 is this phase and it is nine lines of prose; read it exactly** (spec:240–252), then §5's chunking and its "doc-comment problem" (spec:153–180), §8's retrieval and the floor (spec:209–236), §12's testing (spec:280–288), §3's deterministic ids (spec:87–89), §10 (spec:256–263), §11 (spec:267–276), §13 (spec:292–307) and §14's two open questions this phase is required to close (spec:315–316). §2 names `apps/evalrunner` and says what it is for in one sentence (spec:43), and that sentence is a constraint: it runs the *same* retriever the gateway serves from.

## What §9 decides, and what this plan may therefore not do

§9 is nine lines of prose. Five of them are decisions with a plausible-looking opposite that a plan could ship without noticing, and each of the five has already been named as a trap by an earlier phase's measurement.

### 1. The golden set is derived mechanically. Not curated, not cleaned, not rewritten.

Spec:242–244 — "The golden set is **derived mechanically from the corpus**: for every exported symbol carrying a doc comment, the question is the prose and the correct answer is that symbol's span. Generated, not hand-picked, so the questions cannot be authored to flatter the chunker under test."

The tempting implementation is to improve the questions. Doc-comment prose does not read like a question — `Get returns the thing named n.` is a statement, and a plausible-sounding pre-pass turns it into "How do I get the thing named n?". Another turns it over to a model. A third drops the cases whose prose is one word, on the grounds that `Deprecated.` is not a real question. Every one of those is the author choosing which questions the system is asked, which is the exact failure the word *generated* is there to prevent, and every one of them is invisible in the resulting number.

**What this plan does instead:** the question is `(*ast.CommentGroup).Text()`, verbatim, with nothing removed but the trailing newline `Text()` already adds. Measured — `go/ast` at 1.27.0, on a two-line doc comment:

```
Doc.Text() == "Get returns the thing named n.\nIt returns an error if n is unknown.\n"
```

The `// ` markers are gone because `Text()` removes them; the line break is kept because it is in the prose. That string is the question.

Three consequences, all of which are reported rather than filtered:

- **A one-word doc comment is a case.** `rag.Terms("Deprecated.\n", true)` is `["deprecated"]` — measured. That is a legitimate, hard case and it stays. What the plan owes is the *distribution*: metrics are reported overall and split by question length, so a reader can see how much of a headline is one-word questions rather than being protected from them.
- **A doc-comment question is mostly stopwords.** Measured on the two-line comment above: `rag.Terms(q, true)` is `["get" "returns" "the" "thing" "named" "n" "it" "an" "error" "if" "is" "unknown"]` — five of twelve terms are English stopwords, and P3 measured that the `simple` text-search configuration has no stopword list at all. So the lexical arm's contribution on this golden set is *known in advance to be handicapped*, and any statement about fusion has to carry that.
- **Duplicate prose is kept.** Two symbols with identical doc comments produce two cases with the same question and different answers. Deduplicating is hand-picking; recording the duplicate count is not.

The one thing that is *not* filtering is refusing a case the harness cannot score: a case whose declaration has no span in an arm has no answer in that arm, and counting it as a miss would say the retriever failed where the corpus is empty. Those are a **named category with its own count**, never a miss and never silently dropped. Task 1 measures how many there are; the honest expectation is zero (see "What P6 carries forward"), and a non-zero is a finding.

### 2. The corpus is stripped, so the question comes from a file that is not in it — and the answer's coordinates are not the question's.

Spec:172–175 — "A doc comment normally lives *inside* its span's text, so the query would be a literal substring of the correct document. Both arms would then score near-perfectly on string overlap and the comparison would measure nothing — it would be `grep` wearing a benchmark's clothes." Spec:177 — "**Therefore the eval indexes a corpus with doc comments stripped from span text.**"

P2 shipped that as a **source pre-pass**, not as a post-chunk edit of span text, and recorded why: both arms must chunk byte-identical input, and `StrategyWindow` must never parse (spec:166). The consequence is the subtlest thing in this phase, and it is measured, not argued. On a four-line file:

```
raw   : package p\n\n// Add returns the sum of a and b.\nfunc Add(a, b int) int { return a + b }\n   86 bytes, 4 lines
strip : package p\n\n\nfunc Add(a, b int) int { return a + b }\n                            52 bytes, 4 lines

raw       chunk.Decl  ->  func "Add" 3..4
stripped  chunk.Decl  ->  func "Add" 4..4
```

Line count is invariant. Byte offsets are not (86 → 52). And **the declaration's own range moves**, because a blanked doc comment is no longer a comment and `chunk.Decl` then starts the declaration at its keyword. On a real repository P2 measured this at scale: **506 of `rs/zerolog`'s 1,303 AST spans start later in the stripped corpus than in the production one.** P2 wrote the warning into the shipped test file rather than only into a plan — `packages/shared/chunk/strip_test.go:126–132`:

> "Inside the eval that cannot bite — the corpus is stripped once and both arms chunk the same bytes — but P6 must not harvest gold spans from unstripped source and expect them to name the stripped corpus's rows."

**What this plan does:** `golden.Generate` parses each file **twice**. The raw parse supplies the question (`Doc.Text()`); the stripped parse supplies the answer's line range. The two parses are matched by **ordinal position among `f.Decls`**, with `(kind, symbol)` asserted equal at each ordinal and a refusal if they disagree — because stripping cannot add, remove or reorder a declaration, and if it ever does, the harness must stop rather than mis-key a corpus.

The mutation this design exists to survive is M1.2 in Task 1, and it comes with a warning about its own assertion: under the AST arm, using the *raw* range instead of the stripped one still overlaps the same span, so **hit@k does not move and a hit@k assertion cannot kill it.** It is killed by asserting the recorded range as a value, and by a window-arm fixture where the raw range reaches one window further back than the stripped one does. That is this phase's instance of the failure that has recurred in all four previous phases: the fixture discriminates and the assertion cannot.

**And stripping only covers Go.** Measured: `chunk.StripDocs("NOTES.md", …)` returns its input unchanged and no error. So a repository whose `README.md` or `docs/*.md` repeats a doc comment carries that prose into the eval corpus, in *both* arms, and no amount of Go stripping removes it. That is a real leak class, it is not hypothetical in a documentation-heavy repository, and it is why the leakage probe in Task 3 scans **every indexed span**, not only the Go ones.

### 3. Two arms, one corpus, one commit — and the schema cannot prove it.

Spec:247–248 — "across two arms — AST spans versus fixed windows — over the doc-comment-stripped corpus of §5."

P2 **recommended** that the arms get a database each and explicitly left the decision to P6, and P3 repeated "P6 decides": `RepoID = hash(key, commit)` and `SpanID = hash(repo, path, start, end, digest)` have no room for a strategy (spec:87–89), so indexing one commit twice into one database makes the second arm *replace* the first — P2 proved it live, `TestASecondArmReplacesTheFirstInOneDatabaseLive`. This plan takes the recommendation (see "What P6 carries forward"), which is a decision made here rather than one inherited.

The problem this phase inherits is that **nothing in the schema records which arm produced a corpus, or whether it was stripped.** `kind=file` does not say — P2's finding, and `models.go:48–53` says so in the type's own doc comment. `embed_model` records the embedder and nothing else. So an operator who points both `-ast-dsn` and `-window-dsn` at the same database, or who forgets `STRIP_DOC_COMMENTS=true` on one of the two indexer runs, gets a complete run with plausible numbers and nothing anywhere looks wrong.

**What this plan does instead of trusting a flag:** four checks, three of them exact, that run before any retrieval happens and *refuse* rather than warn.

- **Same database?** `testdb.Name(dsn)` on both, compared. Two DSNs differing only in query parameters name one database. **`testdb.Name` is host-blind** — verified, it parses the URL and returns the path — so two databases with the same name on *different hosts* compare equal and are refused. That is a false refusal, and it is the safe direction: it refuses a legal configuration rather than admitting an illegal one, and the operator can rename. It also returns `""` for a DSN it cannot parse, which would make two unparseable DSNs compare equal — also a refusal, also safe, and `store.New` would have failed on them first. Both are stated rather than discovered.
- **Same commit?** `repos.commit_sha` read from both.
- **Same bytes?** The `(path, blob)` multiset from `files`, compared. This is the check that means "the same corpus": `blob` is the content hash of the bytes the indexer read, and the indexer hashes it *before* stripping (`apps/indexer/cmd/main.go`, `row.Blob = blobHash(body)` precedes the `if ix.strip` block), so the two arms must agree on it exactly. A file-count comparison would not catch a different `MAX_FILE_BYTES`; a blob-set comparison does.
- **Actually two arms?** The span-id sets must differ. If they are equal there is nothing to compare, and the operator has almost certainly indexed the same configuration twice.

And **stripping is verified by its effect, not by its flag**: the leakage probe (Task 3) checks that no golden question's prose appears in any indexed span's text. An unstripped corpus fails it by construction. That is what §9's premise actually asks for, and it is checkable without a new column.

### 4. The floor is calibrated from *the vector arm's cosine*, because that is what `Decide` compares.

Spec:248–249 — "The score floor of §8 is calibrated from the resulting distribution … and recorded with the numbers that produced it."

"The resulting distribution" of *what* is the load-bearing ambiguity, and P3 already resolved the same ambiguity one level down and left P6 an instruction (p3:2171):

> "This plan resolves it by comparing the floor against the **vector arm's cosine similarity** … **P6 must calibrate the same quantity**, or the number it measures will not be the number the code compares."

The reason is arithmetic and it is verified: `rag.Fuse`'s score is `Σ 1/(k + rank)` over the arms that returned the span, so it is a function of **ranks alone** and carries no quality signal — P3 pinned that with `TestFusedScoreCarriesNoQualitySignal`, where a good arm scoring 0.99/0.98 and a junk arm scoring 0.01/0.002 fuse to identical scores. A floor on the fused score is `no_spans` with extra arithmetic.

**State that as ranks, not as a constant.** At `k = 60` a single arm's top hit scores `1/61 = 0.0163934…`; a hybrid top hit at rank 1 in *both* arms scores `2/61 = 0.0327869…`; at rank 1 in one arm and rank 2 in the other it scores `1/61 + 1/62 = 0.0325224…`. **P3 made exactly this mistake and corrected it** (`p3-retrieval.md:1610`): it wrote `1/61` as the fused top, found `0.0325224` because its fixture's top span was rank 1 and rank 2, and recorded that "'the top hit always scores `1/(k+1)`' holds for a single arm; in hybrid the fused top is one of a small set of rank-determined values, which is the same point stated too specifically." Repeating the correction one level up: no single constant is "the hybrid top score", and this plan must not name one as though it were.

**So the calibration operates on `rag.Result.TopScore`**, which `Retriever.Search` sets from `float64(vector[0].Score)` and leaves as `math.NaN()` when the vector arm did not run or returned nothing. Anything this plan proposes that changes that must change `rag.Decide` too, with evidence — and it does not.

Two consequences that a plan could miss:

- **In `RETRIEVAL_MODE=lexical` there is no such number and the floor does not apply.** `Decide` short-circuits: `if !vectorRan { return OutcomeAnswered, "" }`. So a floor sweep in lexical mode is a sweep over a threshold that is never read, and the only refusal reachable there is `no_spans`. The harness must not report a floor sweep for lexical mode; it must report that the floor is inapplicable, which is a different sentence.
- **The floor is inclusive.** `top < f.Value` refuses, so a score *equal* to the floor answers. A sweep that reported the wrong side of that boundary would recommend a number one epsilon off from the one the code uses.

### 5. CI's figures are not quality, and the banner is a product surface, not a comment.

Spec:251–252 — "CI runs the harness on a deterministic fake embedder to prove the mechanics still work end to end, and **the figures that run prints are not quality**."

`embed.Fake` is a hashed bag of words over span text, and P3 stated the consequence in `packages/shared/rag/rag.go`'s own package doc: "under `embed.Fake` … both arms compute lexical overlap, so no end-to-end test can show fusion doing anything." P3's fixture rule 5 says the same thing more sharply: **any test that claims to show fusion working end to end is measuring the fake.**

So the banner is not a sentence in a README. It is:

1. the first key of every artefact the harness writes (`"quality": false`),
2. a `banner` string immediately after it, naming spec §9,
3. the directory the artefact lands in (`docs/eval/mechanics/`, never `docs/eval/runs/`),
4. the embed model in the filename,

and a test — `TestNoMechanicsRunIsCommittedAsAMeasurement` — that walks `docs/eval/runs/` and fails if any file there has `quality: false` or `embed_model: "fake-hashed-bow"`. Four surfaces, because P3's and P4's sweeps both found that a single side effect nothing reads back is the most common surviving mutant in this project.

- **Nothing this phase writes may become production configuration by accident.** Exactly one shipped default changes (`rag.DefaultFloor`, Task 9), it changes only after the numbers exist, and Task 9 owns both the second-order bug that change creates and the seven surfaces it falsifies.

## How to mutate, and what counts as a kill

P1–P4 ran roughly 450 mutations. The audit found **~30 predicted failure messages wrong**, **nine false rationales** (the plan's stated reason for the code was wrong, so the mutation derived from it proved nothing), several void mutations, and one structural finding that has now held four times: **per-task mutation rounds are not enough.** P3's eight tasks each closed with "no survivors" and the whole-branch sweep found about twenty. P4 planned ten mutations, killed all ten, and **all four survivors came from the eleven the sweep added.**

The rules, unchanged from P4 except where noted:

1. **Commit before you mutate.** `git status --porcelain` must be empty before the first `sed`; a mutation reverted against a dirty tree restores the mutant.
2. **The mutant must compile and vet.** `go build ./... && go vet ./...` after applying it. Void kills, each of which has happened at least once in this project: removing an import's only use is a build break; a mutant `go vet` flags as unreachable is void; one that panics or `t.Fatal`s before the assertion is an incident, not a kill; and **a SQL mutation that produces a pgx protocol error rather than different rows is void** — mutate `WHERE repo_id = $1` to `WHERE repo_id = $1 OR TRUE`, never by deletion.
3. **Predicted output is an expectation, not a fact.** Every block below says what the failure is expected to look like. Run it, **paste the observed output into this plan**, correct the prediction. A row still reading as a prediction when the task is done is an unfinished task.
4. **Name the fixture that separates mutant from original, and say why it can.** See the metrics-specific version below.
5. **State the rationale for the code you are mutating.** Nine false rationales have shipped in this project already. If the stated reason is wrong the mutation tests nothing.
6. **If you cannot describe the failing output, the test is not evidence.** "It would be flaky" means redesign until the failure is a comparison against a value. This phase has one place where that rule bites hard — the vector arm's tie-break, Task 5 M5.3 — and the honest answer there is a recorded survivor, not a flaky test.
7. **A kill is an assertion failing.** A `t.Fatal(err)` on the way to the assertion, a panic, or a timeout is an incident.
8. **Assert the discriminating property, not a proxy for it.** New in P4, sharpened here: for a metric, assert the **value**, not the range; assert the **whole confusion vector**, not the cell you expected to move; assert the **recorded range**, not that the retrieval still hit.
9. **A comment claiming safety is the highest-risk line in the file.** Run the counterfactual, paste the output into the commit message, then write the comment. If the counterfactual passes, the claim is false — delete it.

Format, unchanged:

```
**M<n> — <one-line description of the edit>.**
- *Why the code exists:* <the rationale a reviewer can disagree with>
- *Fixture that separates mutant from original:* <which fixture, and why it can>
- *Must fail:* <test name>
- *Expected (verify and correct):* <message>
- *Compiles and vets:* <why the mutant is a behaviour change, not a build break>
```

## Fixtures that can tell a metrics bug from a passing test

**This is the section that decides whether P6 is evidence or theatre.** A metrics harness is the worst possible place for the failure that has recurred in every phase — the fixture discriminates and the assertion cannot — because the natural assertion for a metric is a *range*, and a range survives nearly every mutation of the thing it measures. `0 ≤ MRR ≤ 1` is true of the correct MRR, of an MRR that averages only the cases that hit, of an MRR off by one in the rank, and of an MRR that reports the last gold hit instead of the first.

Eight rules. The first six are this phase's; the last two are P3's and P4's, restated because they apply unchanged.

1. **Every metric assertion is on a hand-computed value, never on a range or a comparison between two runs.** The canonical fixture is three cases with the gold span at rank 1, at rank 3, and not in the list at all. MRR is then `(1 + 1/3 + 0)/3 = 4/9 = 0.444444…`, derivable on paper. Under the mutant that averages only the cases that hit it is `(1 + 1/3)/2 = 0.666666…`; under the mutant that is off by one in the rank it is `(1/2 + 1/4 + 0)/3 = 0.25`. All three are in `[0,1]`, so the range assertion kills nothing and the value assertion kills all three.

2. **A fixture where every case hits at rank 1 cannot detect anything about ranking.** MRR is then 1.0 under the correct implementation *and* under a mutant that returns the reciprocal of the last gold hit, the largest gold rank, or a constant. Every metric fixture in this phase contains at least one case that misses entirely and at least one that hits below rank 1.

3. **A fixture with one gold span per case cannot detect "first gold hit" versus "last gold hit".** And one gold span per case is *not* the shape of this eval: under the window arm a declaration longer than the stride spans several windows, and every one of them is gold. The metric fixtures carry a case with **two gold spans at different ranks**, so reciprocal rank has something to be wrong about.

4. **A fixture whose declaration is wholly inside one window cannot detect an overlap-rule bug.** Range intersection has four ways to be spelled wrong and three of them agree on the containment case. Every gold-set fixture contains a declaration **wholly inside** a window, a window **wholly inside** a declaration (the sub-windowed case — measured below), a declaration **overlapping a window's start**, and one **overlapping its end**.

5. **A fixture with no doc comments generates no cases at all**, so it cannot detect anything about the golden set. Conversely, a fixture where every declaration is documented cannot detect the *exclusion* rules — an unexported symbol, a symbol with no doc comment, an import declaration. Every golden fixture has all four shapes and asserts on the case *list*, not on its length: a length assertion passes under a mutant that includes an unexported symbol and drops a documented exported one.

6. **A fixture whose symbol is exported "as a whole" cannot detect per-segment exportedness.** Measured, and this is the fixture nobody writes by accident: `token.IsExported("Store.get")` is **true**, because it reads the first rune. Only a method with an **exported receiver and an unexported name** separates the whole-string check from the per-segment one; `cache.Helper` does not, because both checks refuse it. Every golden fixture carries a documented `Store.get`.

7. **Every corpus fixture holds two repositories** (P3 rule 3, unchanged), and the second repo's spans must be *strictly better* candidates than the target's — for this phase that means the other repository holds a span whose text is the golden question's prose verbatim, so a missing `repo_id` filter changes the answer rather than adding a row nobody looks at. It is also the only fixture that makes the leakage probe's repo scoping observable.

8. **The expected order must disagree with insertion order, path order and id order, and the disagreement must be asserted in the test body** (P3 rule 2, corrected there twice; P3 measured that an unordered result comes back in *path* order, served from `spans_path_idx`). This phase's ranked lists are built by `rag.Fuse`, whose tie-break is `(Score desc, Path, StartLine, SpanID)` — so a fixture whose expected ranking happens to be path order proves nothing about the harness's own ordering.

One more, from the shape of this phase rather than from a rule: **a fixture that needs a model cannot run in CI, and a fixture that runs on `embed.Fake` cannot say anything about retrieval quality.** Every hermetic fixture in Tasks 1–3 is arithmetic over literal ranked lists — no database, no embedder. The live fixtures in Tasks 4–6 run on the fake and assert **mechanics only**: that a case was scored, that a range was recorded, that two runs agree byte for byte. Not one of them asserts that a number is good.

## What P6 carries forward

Each of these is a constraint on the design, not context. Every one was measured by an earlier phase or verified against the code while writing this plan.

- **`chunk.StripDocs` blanks by line, not by byte, and only for `.go`.** Verified: 86 bytes → 52, 4 lines → 4; and `StripDocs("NOTES.md", md)` returns `md` unchanged with no error. It strips **every** `.Doc` group — package doc, `FuncDecl`, `GenDecl`, `TypeSpec`, `ValueSpec`, `ImportSpec`, `Field` — exported or not, and it keeps directives, trailing comments and every comment inside a function body. So the eval corpus still contains in-body prose, and it still contains every non-Go file's prose. The leakage probe scans all of it.
- **`chunk.Decl` starts a declaration at its doc comment, so a documented declaration's range moves under stripping.** Verified: `func "Add" 3..4` raw, `4..4` stripped. On `rs/zerolog`, 506 of 1,303. The golden set's answer range comes from the stripped parse. Nothing else in this project makes that mistake recoverable.
- **A `GenDecl` block is one span, and its symbol is the *first* name it declares.** Verified on a `var ( ErrGone…; errHidden… )` block with a doc on the block and a doc on each spec: one span, `var "ErrGone" 3..9` raw and `4..9` stripped, and *all three* doc comments stripped. So a grouped block can carry several questions pointing at one span, and P2's open question 4 handed P6 the decision with an instruction: "Revisit in **P6** with a count: if a meaningful share of generated questions land on grouped blocks, split per-spec then, with evidence." Task 1 produces the count; Task 8 records the decision.
- **A declaration longer than `MaxDeclLines` has no span carrying its symbol.** Verified: with `MaxDeclLines=10, WindowLines=8, WindowOverlap=2`, a 25-line documented `func Big` produces four `kind=file` chunks with **empty** `Symbol` under the AST arm, and no `func` chunk at all. P2's open question 7 gave the rationale "so a golden question has exactly one correct span rather than N" — **that rationale is false in both directions**: under symbol keying the declaration has *zero* spans, and under range keying it has *four*. This is why gold is identified by **range overlap and never by `spans.symbol`**, and it is a false rationale to record rather than inherit.
- **Stripping can change *how* a declaration chunks, not only where it starts.** P2 measured it and wrote it into `packages/shared/chunk/strip_test.go:126–132`: a declaration 201 lines long *including* a four-line doc comment is **7 sub-windowed `kind=file` chunks (3..203) unstripped and a single `kind=func` span (7..203) stripped**, because blanking drops it under `MaxDeclLines`. So the difference between the two corpora is not only a start line; for declarations near the threshold it is a different number of spans with different kinds. Nothing in the eval sees the unstripped corpus, so this cannot bite inside a run — but it is the second reason a gold span harvested from unstripped source names nothing, and the first reason a `Stats` field counting "cases whose range moved" is not the whole story.
- **Sub-window boundaries move under stripping; whole-file window boundaries do not.** Verified on the same fixture: the AST arm's sub-windows go `3..10, 9..16, 15..22, 21..27` raw and `6..13, 12..19, 18..25, 24..27` stripped, because sub-windowing starts at the declaration's start line — while the window arm's tiles are `1..8, 7..14, 13..20, 19..26, 25..27` in both, because it tiles from line 1 and the line count is invariant. ### Task 1: `apps/evalrunner/internal/golden` — the questions, and the coordinates their answers live in

Everything here is `go/parser` over bytes: no database, no embedder, no network, no clock. It is the only place in the phase that reads unstripped source, and the only place that decides what a case *is*.

**Files:**
- Create: `apps/evalrunner/internal/golden/golden.go`, `apps/evalrunner/internal/golden/generate.go`
- Create: `apps/evalrunner/internal/golden/testdata/{simple,grouped,exported,long,undocumented,notes}.gotxt` (`notes.mdtxt` for the non-Go leak fixture)
- Test: `apps/evalrunner/internal/golden/generate_test.go`

**Interfaces:**
- Consumes: `go/ast`, `go/parser`, `go/token`, `packages/shared/chunk` (`Decl`, `StripDocs`), `packages/shared/models`.
- Produces:
  - `type Case struct { ID, Path, Symbol, Question string; Kind models.SpanKind; Start, End int; RawStart, RawEnd int; Grouped bool; DocOf string }`
  - `type Stats struct { Files, FilesSkipped, Decls, NoDoc, Unexported, Cases, Grouped, DuplicateQuestions int; SkipReasons map[string]int }`
  - `func Generate(path string, src []byte) ([]Case, Stats, error)`
  - `func Normalise(s string) string` — the form the leakage probe compares in
  - `func Leaks(question, text string) bool`

**Decisions, with their reasoning:**

- **Two parses, matched by ordinal.** The raw parse supplies `Question`, `RawStart` and `RawEnd`; the stripped parse supplies `Start` and `End`, which are the coordinates the corpus is in. They are matched by position in `f.Decls` because stripping cannot add, remove or reorder a declaration — and `(Kind, Symbol)` is asserted equal at each ordinal, with `Generate` returning an error if they ever disagree. Matching by symbol instead would look safer and is not: it fails silently the day two declarations in one file share a spelling, and it hides exactly the disagreement the ordinal check is there to surface.
- **`Start`/`End` are the *stripped* range, and `RawStart`/`RawEnd` are recorded beside them.** Both, because the difference is the thing this phase has to be able to report: Task 8's artefact carries how many cases moved and by how many lines, which is the corpus-scale version of P2's "506 of 1,303".
- **The question is `Doc.Text()`, unedited.** No trimming beyond what `Text()` does, no lower-casing, no question-mark appended, no model anywhere near it. `Normalise` exists only for the leakage probe's comparison and never touches `Question`.
- **Exported means every dot-separated segment is exported.** Verified: `token.IsExported("Store.get")` is `true`, so the whole-string check admits a method whose name is unexported as long as its receiver is not. A method a caller outside the package cannot reach is not an exported symbol, and admitting it would put a case in the set whose "correct answer" nobody can ask for.
- **A grouped declaration produces one case per documented exported name, all pointing at the same span.** The block's own `.Doc` produces a case for the declaration's symbol (`chunk.Decl`'s `firstName`); each `TypeSpec`/`ValueSpec` `.Doc` produces a case for that spec's first name. `DocOf` records which — `"decl"` or `"spec"` — and `Grouped` marks the case, so Task 7 can report the share and P2's open question 4 can be closed with a count instead of an opinion. The tempting alternative, one case per declaration, throws away every documented constant in a `const ( … )` block; the other tempting alternative, splitting the *span* per spec, is a chunker change and is out of scope for an eval.
- **`Field.Doc` is not a case.** `StripDocs` blanks struct field docs, so the prose is out of the corpus — but a field is not a top-level declaration, `chunk.Decl` never names one, and there is no span whose answer it could be. Recorded as `NoDoc`'s sibling counter rather than silently ignored.
- **A file that will not parse, or will not strip, produces no cases and is counted with its reason.** It also produces no spans (the indexer `continue`s), so the two agree by construction — but the harness must count it, because "this repository contributed no cases" and "this repository has no documented exported symbols" are different facts.
- **`Leaks` compares normalised forms.** `Normalise` lower-cases and collapses every run of non-alphanumeric bytes to one space. Exact substring containment would catch a one-line doc comment (whose prose survives verbatim inside `// …`) and **miss a multi-line one**, because `Doc.Text()` drops the `// ` from the second line and the raw span text does not. A probe that misses the multi-line case is a probe that passes on the corpus it exists to refuse.

### Task 2: `apps/evalrunner/internal/metric` — hit@k, MRR, the gold set, and the refusal confusion

Pure arithmetic over literal ranked lists. No database, no embedder, no `golden` dependency beyond a line range. **This is the task where the phase is most likely to produce a number that is confidently wrong**, so every assertion here is on a value computed on paper.

**Files:**
- Create: `apps/evalrunner/internal/metric/metric.go`, `apps/evalrunner/internal/metric/gold.go`
- Test: `apps/evalrunner/internal/metric/metric_test.go`, `apps/evalrunner/internal/metric/gold_test.go`

**Interfaces:**
- Consumes: `packages/shared/models` **and `packages/shared/rag`** — see the first decision below; the "models only" this task was first written with is what made `Sweep` a third derivation of the refusal rule. There is no import cycle: `rag` imports `embed`, `metrics`, `models` and `admit`, none of which reaches `apps/`.
- Produces:
  - `type Span struct { ID string; Path string; Start, End int }`
  - `func Gold(path string, start, end int, spans []Span) (lenient []string, strict string)`
  - `func HitAtK(ranked []string, gold map[string]bool, k int) bool`
  - `func ReciprocalRank(ranked []string, gold map[string]bool) float64`
  - `func MeanOverAll(xs []float64) float64`
  - `type Outcome struct { CaseID string; TopScore float64; Hits int; VectorRan bool; GoldRank int; AnswerHasGold bool; Scoreable bool }`
  - `type Confusion struct { AnsweredWithGold, AnsweredWithoutGold, RefusedWithGold, RefusedWithoutGold, Unscoreable int; ByReason map[rag.Reason]int }`
  - `func Sweep(outcomes []Outcome, floors []float64) []Confusion`

**Decisions, with their reasoning:**

- **`Sweep` calls `rag.Decide`. It does not spell the rule.** This task was first written with `Outcome` carrying only `TopScore` and a consumes list closed at "`models` only", which made `Sweep` structurally unable to see two of `Decide`'s four inputs — and therefore a **third** independent derivation of the refusal rule, in the same phase whose Global Constraints say a P6 that reimplements the refusal rule has found a P3 defect, and whose Task 4 exists to reduce two derivations to one. The bias was not neutral and it all ran one way:
  - a `no_spans` case has `hits == 0` and a `NaN` top score. `Decide` refuses it at every floor; a `TopScore`-only sweep answers it at every floor, because `NaN < f` is false.
  - an `unscored` case (`NaN` top, hits present) is the same story: refused by `Decide`, answered by the sweep.
  - in lexical mode `Decide` short-circuits to *answered* whatever the score; a `TopScore`-only sweep refuses everything under the floor.

  Every one of those lands in `AnsweredWithoutGold`, which is exactly the cell Task 9's calibration criterion balances against — so the sweep would have pushed the recommended floor in one direction and nothing would have looked wrong. `Outcome` therefore carries `Hits` and `VectorRan`, and `Sweep` is `rag.Decide(rag.Floor{Value: f}, o.Hits, o.TopScore, o.VectorRan)` and a tally. `Confusion.ByReason` records which reason each refusal carried, because `no_spans` and `below_floor` are different facts about a corpus and a floor sweep that cannot tell them apart cannot say what the floor is doing.
- **Gold is range overlap in one file, never `spans.symbol`.** Three verified reasons. The window arm's spans all carry an empty symbol, so a symbol key finds nothing there and the two arms would be scored by different rules. A declaration longer than `MaxDeclLines` has no span carrying its symbol under the AST arm either — verified, four `kind=file` chunks with empty symbols and no `func` chunk. And P2's stated rationale for leaving that symbol empty ("so a golden question has exactly one correct span rather than N") is false in both directions, so it cannot be relied on.
- **Two gold definitions are reported, not one.** `lenient` is every span in the same file whose range intersects the declaration's; `strict` is the single one with the largest overlap, ties broken by lower start line then span id. Both, because they disagree in a way that is not neutral between the arms: a 100-line declaration is one AST span and three window-arm windows, so the lenient rule gives the window arm three chances where the AST arm gets one. Reporting only the lenient number would hand the window arm an advantage that is an artefact of the rule; reporting only the strict number would penalise it for tiling. **Task 8's artefact carries the mean gold-set size per arm beside every metric**, so a reader can see how much of any difference is target size.
- **`ReciprocalRank` is the reciprocal of the rank of the *first* gold hit, and 0 when there is none.** Zero, not "excluded" — MRR is defined over all cases, and averaging only the ones that hit reports a different, higher, and wrong number that no range assertion catches.
- **`MeanOverAll` is a named function rather than an inline division.** It exists to have something to mutate: the failure it guards is one line long and invisible in a plot.
- **`Scoreable` is a per-case field, not a filter.** A case with no gold span in an arm cannot be right or wrong there; it is counted in its own cell and excluded from the denominators, and the artefact says how many. The honest expectation is zero, **and the reason is not the obvious one.** "Every line of every indexed file is covered by some span" is **false for the AST arm** — measured: a 15-line file whose only declarations are a documented `var` block and a documented `type` yields exactly two chunks, `3..9` and `11..15`, so lines 1, 2 and 10 are covered by nothing, because `astChunks` emits per *declaration* and not per line. The reason the expectation still holds is different and narrower: **a case's answer range *is* a declaration's range**, and every declaration `chunk.Decl` accepts produces either one span or a run of sub-windows covering it. A non-zero `Unscoreable` is therefore a finding about the chunker, not about coverage.
- **`Sweep` takes recorded outcomes, never a retriever.** Retrieval does not depend on the floor, so the whole floor curve comes from one retrieval pass. That is not only cheaper: it makes the calibration **reproducible from the committed artefact** without re-running an embedder, which is what "recorded with the numbers that produced it" (spec:249) has to mean if it is to mean anything.
- **The confusion is four cells and they are named in both directions.** `RefusedWithGold` is the system refusing when it should have answered. `AnsweredWithoutGold` is the system answering when it should have refused. Reporting one without the other is how a floor gets tuned to zero or to one.
- **`AnswerHasGold` is about the assembled answer, not the ranked list.** `rag.Assemble` drops spans past `Budget.MaxSpans` (default 5) and past `MaxChars`, so a gold span ranked 7th is retrieved and not cited. "Answered without citing the right span" is the outcome a user experiences, and scoring the ranked list instead would report a system that is better than the one that ships.

**The canonical metric fixture, and why every number in it is chosen:**

```
case A: ranked [s1 s2 s3 s4 s5], gold {s1}          -> RR = 1/1 = 1
case B: ranked [s1 s2 s3 s4 s5], gold {s3, s5}      -> RR = 1/3 (NOT 1/5)
case C: ranked [s1 s2 s3 s4 s5], gold {s9}          -> RR = 0
MRR over A, B, C = (1 + 1/3 + 0) / 3 = 4/9 = 0.4444444444444444
```

Case B has **two** gold spans at different ranks, which is the window arm's real shape and the only thing that separates "first gold hit" from "last". Case C is the miss that puts a zero in the numerator and a one in the denominator. Under the three mutations below the value is `(1 + 1/3)/2 = 0.6666…` (skip the zeros), `(1/2 + 1/4 + 0)/3 = 0.25` (off by one in the rank) and `(1 + 1/5 + 0)/3 = 0.4` (last gold hit rather than first) — all inside `[0,1]`, which is why the assertion is `4.0/9.0` and not a range.

### Task 3: `apps/evalrunner/internal/corpus` — the contract between the arms, and the probe that refuses

The four checks that make "both arms index the same corpus at the same commit" a property rather than a promise, and the leakage probe that makes "the corpus is stripped" checkable without a new column.

**Files:**
- Create: `apps/evalrunner/internal/corpus/corpus.go`, `apps/evalrunner/internal/corpus/leak.go`
- Test: `apps/evalrunner/internal/corpus/corpus_test.go`, `apps/evalrunner/internal/corpus/corpus_live_test.go` (`//go:build live`)

**Interfaces:**
- Consumes: `packages/shared/store`, `packages/shared/testdb`, `apps/evalrunner/internal/golden`.
- Produces:
  - `type Reader interface { Commit(ctx, repoID) (string, error); FileBlobs(ctx, repoID) (map[string]string, error); SpanRanges(ctx, repoID) ([]metric.Span, error); SpanTexts(ctx, repoID, after string, limit int) ([]TextRow, string, error) }`
  - `type Arm struct { Name, Database, RepoID string; Read Reader }`
  - `type Report struct { Commit string; Files, Spans map[string]int; SharedSpanIDs int; Leaks []Leak }`
  - `type Leak struct { CaseID, SpanID, Path string }`
  - `var ErrSameDatabase, ErrCommitMismatch, ErrFileSetMismatch, ErrIdenticalArms, ErrSourceMismatch, ErrLeaked error`
  - `func Verify(ctx context.Context, a, b Arm, src map[string]string) (Report, error)`
  - `func Probe(ctx context.Context, a Arm, cases []golden.Case) ([]Leak, error)`

**`Arm` takes a `Reader`, not a `*store.Store`.** `store.Store` is `struct{ pool *pgxpool.Pool }` with the pool unexported — verified — so a concrete `*store.Store` cannot be faked, and the four hermetic tests below would silently become live tests or would not exist. P3 hit this exact wall and solved it the same way: `rag.Searcher` is an interface, and `retrieve.go`'s comment says why in terms that apply here unchanged ("spec §9 requires the eval to run *this* retriever rather than a reimplementation of it, and P2 left open that the eval's two arms may end up in a database each"). `corpus` gets the same seam.

**Three new shipped `store` reads, not one.** This task was first written claiming `FileBlobs` was "the only shipped-code addition"; that is false, because `store` has no way to enumerate a repository's spans at all — verified against the complete read set. `metric.Gold` needs a file's whole span set, `ErrIdenticalArms` needs the span-id set, and `Probe` needs every span's text; `rag.Result` cannot supply any of them, since it holds only the spans that survived the trim and `rag.Fused` carries no `EndLine`. So:

- `func (s *Store) FileBlobs(ctx context.Context, repoID string) (map[string]string, error)` — path to blob, scoped to one repo. `RepoStats` gives counts; counts are not the check.
- `func (s *Store) SpanRanges(ctx context.Context, repoID string) ([]SpanRange, error)` — `(id, path, start_line, end_line)` for a whole repo, ordered `(path, start_line, id)`. Ordered in SQL rather than in Go because the id set and the gold sets both have to be reproducible across runs, and an unordered read is P3's finding about `spans_path_idx` waiting to happen.
- `func (s *Store) SpanTexts(ctx context.Context, repoID, after string, limit int) ([]SpanText, string, error)` — keyset-paged `(id, path, text)`, returning the next cursor. Paged rather than whole-corpus because the probe reads every byte of text a repository has; `rs/zerolog` is ~1 MB and a repository ten times that must not be one allocation.

Each gets its own mutation block below. Three exported reads added to a shipped package inside an eval is a real cost and it is stated rather than buried: the alternative is the harness opening its own `pgx` connection beside the store, which is a second place for a repo filter to be forgotten.

**Decisions, with their reasoning:**

- **The source the questions came from is bound to the corpus by hash, or the whole run is unanchored.** `golden.Generate(path, src)` is the only reader of unstripped source in the phase, and until this check existed nothing said where `src` came from: the runner's flags named two DSNs and a repo id, spec:9 forbids the harness cloning, and the indexer deletes its checkout when the job ends (`clone.go`). So the operator points `-src` at *a* checkout, and if it is a different commit — or merely a different *file set*, because they used `filepath.Walk` where the indexer uses `walk.Files` plus `indexable` — every case's range names lines the corpus does not have. **And the leakage probe does not fire on that**, because a question generated from the wrong file is not prose that appears in the corpus; it is prose that appears nowhere. The failure is a whole run of plausible numbers with nothing behind them.

  The check: re-hash every file `golden` read with the indexer's own `blobHash` — verified to be git's blob hash, `sha1("blob %d\x00" + body)`, and verified to run *before* stripping (`main.go`: `row.Blob = blobHash(body)` precedes the `if ix.strip` block) — and compare against `FileBlobs` for **both** arms. A file the harness read that no arm indexed, or a blob that disagrees, is `ErrSourceMismatch` naming the path. This is the same evidence the arm-to-arm file check uses, pointed at the third party nobody was checking.
- **Every check refuses; none warns.** A warning on a run that produces a JSON file full of numbers is a warning nobody reads. Each failure returns a distinct sentinel error naming which rule failed, matching spec:258's rule for admission rejections — "naming **which rule** failed, never a generic refusal".
- **The file check is on `(path, blob)`, not on counts.** `blob` is hashed from the bytes the indexer read, *before* stripping — verified at `apps/indexer/cmd/main.go`, where `row.Blob = blobHash(body)` precedes the `if ix.strip` block — so two arms over one commit must agree on it exactly. A count comparison passes when one arm ran with a different `MAX_FILE_BYTES` and skipped a file the other read.
- **The probe scans every span's text, not the gold span's and not the top hit's.** The prose can be anywhere: a non-Go file (`StripDocs` passes `.md` through unchanged — verified), a duplicated comment in a test file, an in-body comment quoting the doc. Any of those makes the question findable, and the probe's job is to say the corpus is unusable, not to say the gold span is clean.
- **The probe reads span text in bounded pages and holds only the normalised questions in memory.** `rs/zerolog` is 1,303 spans and about a megabyte; a repository ten times that is still tractable, and the alternative — one SQL query per case — is `len(cases)` round trips. The bound is a constant with the measured corpus size in its comment, and a corpus over it is refused with a message saying so rather than being scanned to exhaustion.
- **A leak is reported with its `(case, span, path)`, and the run stops.** A count alone cannot be acted on; `path` is what tells an operator whether the leak is a missed `.go` file or a `README.md`, which are different problems with different fixes.
- **The identical-arms check is on the span-id *set*, not on the span count.** Two arms can coincidentally produce the same number of spans; they cannot produce the same ids unless they chunked identically. P2 measured that three spans are shared between the arms on the indexer's fixture repo, so a nonzero intersection is normal and `SharedSpanIDs` is reported rather than refused.

### Task 6: The artefact — where numbers live, in what format, and how a reader tells mechanics from measurement

Spec:249 — "recorded with the numbers that produced it". This task decides what that file is, where it lives, how long it stays, and what stops a CI mechanics run from being read as a measurement at a glance.

- Create: `apps/evalrunner/cmd/artefact.go`

- Test: `apps/evalrunner/cmd/artefact_test.go`

**Decisions, with their reasoning:**

- **One JSON file per run, in `docs/eval/runs/<date>-<owner>-<repo>-<embed-model>.json`.** JSON because the sweep, the confusion matrices and the per-case records are structured and a reader will want to diff two runs; a Markdown table would have to be regenerated by hand and would drift from the numbers it summarises. The filename carries the embed model because that is the single fact that decides whether the file is a measurement.
- **A mechanics run goes to `docs/eval/mechanics/`, and nothing there is committed — the directory is gitignored.** An earlier draft kept one committed mechanics artefact "because Task 5's determinism test needs a stable comparison point". **That reason is false:** Task 5's test runs the harness twice in one process against one corpus and compares the two outputs to each other, so it needs no committed file at all. And the file it would have justified is the exact object M5.2 and `TestNoMechanicsRunIsCommittedAsAMeasurement` exist to keep out of the repository — a `quality: false` artefact sitting in `docs/eval/`, one `git mv` from looking like a measurement. So: `docs/eval/mechanics/` is a documented destination for a developer's local run, it is in `.gitignore`, CI writes to a temp directory, and the repository holds no fake-embedder artefact anywhere.
- **`quality` is the artefact's first key and `banner` its second.** A reader who opens the file, greps it, or sees it in a diff hits the label before any number. For a fake run: `"quality": false` and `"banner": "MECHANICS ONLY — spec §9: the figures this run prints are not quality."`. For a real run: `"quality": true` and an empty banner, because a banner that is always present is a banner nobody reads.
- **Four surfaces, because P3's and P4's sweeps both found single side effects surviving.** The field, the banner string, the directory, and the filename. `TestTheArtefactSaysWhatItIsOnEverySurface` asserts all four together.
- **`TestNoMechanicsRunIsCommittedAsAMeasurement` walks `docs/eval/runs/`** and fails on any file with `quality: false` or `embed_model: "fake-hashed-bow"`. It is a test about the repository, not about a function, and it is the only thing that catches the mistake in M5.2.
- **Reproduction is in the file, not in a commit message.** The artefact records: the exact command line; `git rev-parse HEAD` of codetrail at run time; the repository remote and commit; both DSNs' *database names* (never their credentials); the chunk options and the strip flag for each arm; the embed provider, model and dim; the retrieval mode, `k`, candidates, split flag and limit; the answer budget; the indexer's per-job counters (`vanished`, `unstrippable`, `tokenless`, `unparsed`) for each arm, copied from its log line; and `store.RepoStats` for each arm. A number whose configuration is not in the same file is a number nobody can reproduce.
- **Retention: every real run is kept.** The `runs/` directory is append-only in practice — three repositories times a handful of configurations is a few dozen small files, and the whole point of the phase is that a later reader can see what the numbers were before someone changed something. `docs/eval/README.md` is a hand-maintained index table, newest first, with one line per run and a link; it lists real runs only.
- **Per-case records are in the artefact, not in a sidecar.** They are what makes the floor sweep reproducible without an embedder, and splitting them out is how a summary and its evidence drift apart.

## Open questions

Nothing here is blocking. Each is something the spec does not settle, with the tradeoff and a recommendation, so a reviewer can disagree with a decision rather than discover it.

1. **What counts as "that symbol's span" under the window arm.** §9 says "the correct answer is that symbol's span" (spec:243) and also says the comparison is "AST spans versus fixed windows" (spec:247). Under fixed windows there is no such span: every row is `kind=file` with an empty symbol.
   *Recommendation:* **range overlap in one file, reported under two rules** — lenient (every overlapping span) and strict (the largest overlap) — with the mean gold-set size printed beside every metric. The lenient rule is not neutral: a 100-line declaration is one AST span and three windows, so it hands the window arm three chances. The strict rule is not neutral either: it penalises a chunker for tiling. Publishing one without the other is choosing a winner with a definition.

2. **Whether a grouped declaration should produce several questions or one.** §9 says "every exported symbol carrying a doc comment"; P2 makes a `var ( … )` block one span whose symbol is its first name.
   *Recommendation:* several questions, one span, with `Grouped` and `DocOf` recorded so the share is a number. P2 asked P6 for exactly this count. If the share is material and the grouped cases score materially worse, that is evidence for a per-spec chunker change in P7 — recorded, not made here.

3. **How many repositories a calibration needs.** §9 says "calibrated from the resulting distribution" and names no corpus.
   *Recommendation:* **three, named before the run, all published.** One is a style, not a distribution. Three is not statistics either, and the README says so — the honest claim is the per-repository spread, not a confidence interval nobody computed.

4. **Whether the harness should build its own corpora.** §2 says the evalrunner runs the same *retriever*; it says nothing about the indexer.
   *Recommendation:* **it should not.** The corpora come from the shipped indexer, run twice, and the harness *verifies* rather than trusts. Building corpora in-process would duplicate `walk.ReadRegular`, the `indexable` guard, the batching and the vanished-file handling, and the duplicate would drift. The cost is that the strip flag and the strategy are not in the database, which is what Open question 5 is about.

5. **Nothing in the schema records which arm produced a corpus or whether it was stripped.** `kind=file` does not say (P2), `embed_model` says only the embedder.
   *Recommendation:* **do not add a column in P6.** The leakage probe checks stripping by its effect, which is stronger than a flag, and the arms are named on the command line and cross-checked against a span-set difference. A `corpus_config` column is defensible and it is a schema change made inside an eval, which is the wrong phase for it. Revisit in P7 if incremental re-index needs to know what a corpus is.

6. **`vectorSearchSQL` has no tie-break and `LexicalSearch` does.** §9 asks for a deterministic CI run.
   *Recommendation:* measure first (Task 5 M5.3). If the order is already stable on a small corpus, record that the *guarantee* is absent even though the behaviour is stable, because a corpus large enough to use the HNSW index has no such promise. If it is not stable, add the tie-break and re-run P3's `EXPLAIN` test to confirm the index path survives. Either way the decision is in the plan with its measurement, not in a comment.

7. **Doc-comment prose is not the question a user types.** `Sampler defines an interface to a log sampler.` is a statement about a symbol; P3's own real question was "how does the sampler decide to drop an event". §9 chose the generated set precisely because a hand-written one can be authored to flatter, and that trade is real in both directions.
   *Recommendation:* keep the generated set as the headline and **say what it measures** — "can the system find the symbol this sentence describes", which is a proxy for "can it answer a question about this code". P3's seven hand-written questions stay in the README as a separate, smaller, explicitly hand-picked set, labelled as such, so a reader can see both. Do not merge them; a hand-picked set inside a generated one contaminates the number that was generated to be uncontaminated.

8. **The lexical arm is handicapped on this golden set by construction.** Verified: a doc-comment question tokenises to twelve terms of which five are English stopwords, and `simple` has no stopword list.
   *Recommendation:* report it as a property of the experiment rather than correcting for it. A stopword list is a change to the arm, and measuring a changed arm in the phase that builds the measurement means reporting on a system nobody shipped. The honest form is: "on this question distribution, the lexical arm contributes `<x>`, and here is why that number is a lower bound."

9. **`RETRIEVAL_CANDIDATES` is 40 because that is pgvector's `hnsw.ef_search` default, and the harness could raise it.**
   *Recommendation:* headline at the shipped default; sweep it and publish the curve. Raising it improves the numbers by doing more work, and a headline measured at a depth production does not run is a headline about a different product.

10. **What happens to `docs/eval/runs/` over time.**
    *Recommendation:* append-only, no rotation. A few dozen small JSON files, and the whole value of the phase is that a later reader can see what the numbers were before something changed. Revisit if it exceeds a megabyte, which at these sizes is many years.

11. **Whether the harness should report per-kind metrics.** A `func` span, a `type` span and a sub-window are different retrieval problems.
    *Recommendation:* yes, as a breakdown in the artefact and not in the headline. It costs one grouping and it is the first thing anyone will ask when a number disappoints. Keep it out of the README, which should carry one number per arm per mode.

12. **What P6 does if the AST arm loses.** The project's first sentence says code does not chunk like prose and that codetrail *measures* that rather than asserting it (spec:16–18).
    *Recommendation:* publish it, in the README, in the same words as if it had won. The design document's own framing is that asserting the answer is the failure this project is built to avoid, and the phase has no value at all if its result is conditional on which way it comes out.

## What the spec leaves underspecified or in tension

Recorded so a reviewer sees them as findings rather than as choices made quietly. Two of these are the spec disagreeing with shipped code, and one is the spec disagreeing with itself.

- **§9's definition of a correct answer is well-formed for only one of the two arms it names.** Spec:243 says "the correct answer is that symbol's span"; spec:247 says the measurement runs "across two arms — AST spans versus fixed windows". A fixed window is not a symbol's span — every window row is `kind=file` with an empty `symbol`, verified — so taken literally §9 defines correctness for the AST arm and leaves the baseline arm undefined. This plan resolves it with range overlap and reports both a lenient and a strict rule with their gold-set sizes, because the choice between them is not neutral between the arms and hiding it inside one number is choosing a winner with a definition.

- **§5 says the eval strips doc comments "from span text"; P2 shipped a source pre-pass, and that changes where the answer is.** Spec:177 — "the eval indexes a corpus with doc comments stripped **from span text**". Read literally, that is a post-chunk edit: chunk first, then remove the prose from each span's `text`, which would leave every AST span's *range* identical to production's. P2 shipped the opposite — strip the source, then chunk — and gave two reasons that hold (spec:166's "`Window` never parses at all" cannot survive a chunker that parses to strip; and both arms must chunk byte-identical input). The consequence is the one this phase is built around and it is measured: a documented declaration's span starts at its doc comment, so 506 of `rs/zerolog`'s 1,303 AST spans start later in the stripped corpus. A reader of §5 alone would harvest gold spans from unstripped source and would be wrong for exactly the documented declarations the golden set is made of. P2 wrote the warning into `strip_test.go` rather than only into a plan; this plan makes it Task 1's load-bearing test.

- **§9's "calibrated from the resulting distribution" does not say of what, and the only reading that works contradicts §8's own fusion.** Spec:213 defines retrieval as reciprocal-rank fusion; spec:230 says a refusal happens "when the top score falls under a floor". An RRF score is a function of ranks alone — verified, `1/61 + 1/62 = 0.0325224…` for a hybrid top hit whether it is perfect or worthless — so a floor on the fused score is `no_spans` with extra arithmetic. P3 resolved it toward the vector arm's cosine and left P6 an instruction. This plan follows it. Anyone reading §8 and §9 alone would calibrate a quantity `rag.Decide` never reads, and the sweep would look fine.

- **§9 asks for a deterministic CI run and the shipped vector search cannot promise one.** Spec:251 — "a deterministic fake embedder". `embed.Fake` is deterministic and pinned by value; `vectorSearchSQL` is `ORDER BY embedding <=> $2::vector LIMIT $3` with no tie-break, while `LexicalSearch` has `ORDER BY score DESC, path, start_line, id`. Two spans at equal distance come back in an order the planner chooses, and a hashed bag of words over similar text produces exact ties. §9's word "deterministic" describes the embedder; the property it needs is of the whole pipeline. Task 5 measures it and decides.

- **§9 wants the golden set to regenerate and the numbers to be recorded, and those pull apart.** Spec:245 — "regenerates as the corpus changes"; spec:249 — "recorded with the numbers that produced it". A set that regenerates is a set whose numbers are not comparable across corpus versions. This plan resolves it by pinning the corpus at a commit and committing the generated cases *with* the numbers, so a later reader can tell "the retriever changed" from "the question set changed". Neither half of §9 says to do that.

- **§5 cites the wrong section for the golden set.** Spec:172 — "The eval's golden set is 'doc-comment prose → the symbol it documents' (§8)." §8 is *Retrieval, citations, answering* and says nothing about a golden set; §9 defines it. Small, but it is the cross-reference a reader follows to find out what the corpus is *for*, and following it lands on the retrieval section — which is also where the floor lives, which is exactly the confusion the previous bullet is about. Read §9.

- **§14 puts the floor's value in P6 and §8 describes it as already measured.** Spec:231 — "a refusal when the top score falls under a floor that the eval measures rather than picks" — is written in the present tense about a phase that had not run. P3 caught the same tension in the README and replaced the wording; the spec still reads that way, and it is why P3's `Calibrated` flag exists at all.

- **§2 says `apps/evalrunner` "Runs the *same* retriever the gateway serves from", and the gateway's refusal rule is not in the retriever.** Spec:43. `rag.Retriever.Search` never calls `Decide`; the handler does, at `read.go:347`, with four arguments it assembles itself. So "the same retriever" gets ranking and fusion and stops one call short of the outcome the eval is measuring. Task 4 closes it with one derivation and two callers; §2 does not say to.

- **§11's counters still have nowhere to live in the indexer**, and this phase depends on three of them. `vanished`, `unstrippable`, `tokenless` and `unparsed` are a log line, not a metric, and the artefact copies them out of a log by hand because there is no endpoint to scrape. P3 recorded the gap and P4 added four more instruments to it *(**three**, not four — corrected 2026-09-06; see the note at the head of this file.)*; P6 is the first phase whose *output* is worse because of it.

- **§9 says nothing about how many repositories a calibration needs**, and §14 says the floor is "measured in P6" as though the measurement were one number. A floor is a property of a corpus and an embedder, and the spec's phrasing invites a single-repository run reported as a fact. This plan names three before measuring any and publishes all three; that discipline is not in the spec and should be.

- **`rag.Fuse`'s doc comment calls `k` "the parameter P6 sweeps" and `Retriever`'s calls every field "configuration a deployment sets and P6 sweeps".** Both are true and both are now claims this phase has to make good on or delete. If a sweep is not run for a knob, the comment naming P6 must be corrected rather than left standing — P2 corrected twelve drifted comments, two of them introduced by commits fixing others, and these are the same shape aimed at this phase.
