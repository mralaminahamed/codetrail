**Goal:** Give the four verbs spec §2 names for `apps/console` — **submit, watch indexing, ask, jump to source** — a browser, plus the symbol-graph browsing P4's three endpoints already serve. The console is a *renderer of the API's distinctions*, not a second opinion about them. Three distinctions carry the whole phase: a **refusal is not an error** (spec:262), a **citation is the claim and the permalink is only a convenience** (spec:217–226), and a **staleness sentence is a specific claim written by the server**, not a mood the client sets. Every one of those has a plausible-looking opposite that ships without anybody noticing, and each opposite destroys work a previous phase spent a task preserving.

**Architecture:** One new directory, `apps/console`, and no new Go package. Vite builds a static bundle; React 19 + TypeScript render it; Tailwind v4 styles it. A single `src/api/` module owns every request and is the only place a network shape becomes a TypeScript value — it exposes an `Outcome<T>` discriminated union in which **a refusal cannot be constructed**, because a refusal is a *value of the ask endpoint*, not a member of the error union. That one type decision is what makes spec:262 a compile-time property rather than a code-review habit. Views are dumb: they receive a parsed value and render it. The only stateful machinery in the phase is the job poller, and it is hand-written because its policy — staged intervals, a hard ceiling, visibility awareness, and three different responses to 404, 5xx and a dead network — is exactly the thing a caching library would hide. The gateway gains **one Go file, and it is a test**: a `-tags=live` fixture emitter that writes the console's JSON fixtures from the real handlers, so a fixture cannot drift from the API it claims to describe.

**Tech Stack:** Node 22 LTS, Vite 7, React 19, TypeScript 5 (`strict`), Tailwind v4 (CSS-first: `@import "tailwindcss"` plus `@tailwindcss/vite`; no `tailwind.config.js`, no PostCSS file), React Router v7, Vitest + jsdom + `@testing-library/react` + `@testing-library/user-event` + `@testing-library/jest-dom`, MSW for HTTP, `jest-axe` for the automated a11y floor, ESLint with `typescript-eslint`, `eslint-plugin-react-hooks` and `eslint-plugin-jsx-a11y`.

**Build tool, justified in one line:** Vite — the repository's `.gitignore` already ignores `dist/`, `.vite/` and `node_modules/`, so it was scaffolded expecting exactly this, and Vite's dev/preview proxy is what makes the console **same-origin** with the gateway without adding CORS to a public, unauthenticated API that clones strangers' URLs.

**Spec:** `docs/superpowers/specs/2026-08-31-codetrail-design.md`. **§2's console row is one line and every word in it is a task** (spec:42). Then §8 in full (spec:209–236) — retrieval, the citation tuple, staleness, extractive-or-refused, and "the response names which one answered it"; §10 in full (spec:256–263) — the four HTTP outcomes and the refusal/error split; §11 (spec:267–276); §12 (spec:280–288, and spec:287 is why this document is shaped the way it is); §13 (spec:292–307, P5 at spec:301); §14 (spec:311–321, and spec:315 is why the floor may not be presented as meaningful).

**Predecessor:** `docs/superpowers/plans/2026-09-02-p4-symbol-graph.md`. P4 merged at `cd97e2d`. P4's closing finding is this plan's opening constraint: *"§13 puts the console in P5 and the LLM loop in P7, so P4's endpoints have no consumer for two phases. ## What the spec decides, and what this plan may therefore not do

Five clauses. Each is a decision, each has an opposite that a competent console ships by accident, and each opposite is invisible in a happy-path screenshot.

### 1. A refusal and an error are **distinct outcomes**. Not two shades of failure.

Spec:262 — "Refusal and error are **distinct outcomes** in metrics, so 'we had nothing to say' never hides inside 'we broke'." The gateway spent a task on it: `read.go:162–165` says in the code that a refusal is a `200` because "expressing 'we had nothing to say' as an HTTP error would file it inside every error-rate panel in existence, which is the hiding §10 exists to prevent."

The console's opposite is one line long: a `try/catch` around `ask()` whose `catch` renders a red box, plus a `if (body.refused) throw` that feeds it. Nothing about that looks wrong on review and it undoes the whole of P3's refusal work at the last mile.

**What this plan does instead.** The parse layer returns

```ts
type Outcome<T> =
  | { kind: "ok"; value: T }
  | { kind: "rejected"; rule: string; detail: string }        // 400
  | { kind: "missing"; detail: string }                       // 404
  | { kind: "gone"; detail: string }                          // 410
  | { kind: "failed"; detail: string; requestId: string | null } // 5xx
  | { kind: "unreachable"; detail: string };                  // no response at all
```

and `AskResult = Answered | Refused` is a *value carried inside `kind: "ok"`*. A refusal therefore cannot reach the error renderer without someone writing `{ kind: "failed" }` by hand — which is exactly the mutation Task 2 applies, and exactly what a test must kill. Three properties fall out, and all three are tests:

- **The refusal panel is `role="status"` and carries the floor block; the error panel is `role="alert"` and carries a request id.** Neither can render the other's evidence, so each test asserts its own content *and the absence of the other's*.
- **A refusal is not counted, styled or worded as a failure anywhere.** Task 6 asserts the refusal region contains no `alert` role and no retry control.
- **`refused` is the discriminant, not the presence of `answer`.** An answered response can carry `answer: ""` — see the `citations: null` finding below — so branching on truthiness of `answer` reads an empty answer as a refusal. Task 2's parser branches on `refused` and Task 6's fixture is the empty answer.

### 2. The score floor is **uncalibrated**, and P6 is where it becomes a number.

Spec:315 — "**The score floor's value.** Measured in P6; picking it earlier would be guessing." The shipped default is `rag.DefaultFloor()` = `{Value: -1, Calibrated: false}` (`decide.go:25`), and `floorView.Calibrated` is on the wire for exactly this reason (`read.go:102–108`).

**Measured consequence the console must not paper over:** at the default floor, `below_floor` is **unreachable**. `Decide` refuses when `top < f.Value` (`decide.go:87`) and a cosine similarity is never below `-1`. So a console demoed against a default deployment will only ever see `no_spans` and `unscored`, and any UI that draws "your score vs the floor" is drawing a bar whose right-hand end is off the bottom of the scale.

**What this plan does.** No score-versus-floor gauge, bar, meter or percentage while `floor.calibrated === false`. The floor is rendered as a sentence, and the sentence says it is not a measurement. Words are fixed in Task 6 and pinned by test.

**And what it cannot do, because the gateway will not let it.** The obvious way to prove the suppression is conditional — rather than a feature the UI never had — is a `calibrated: true` fixture. That fixture cannot be emitted honestly: `detail()` hard-codes the disclaimer. `read.go:390–393` returns

```
"The best match scored under the configured floor of " + <value> +
". That floor is not calibrated; its value is measured in P6."
```

**unconditionally**, never reading `f.Calibrated`. So a below-floor refusal emitted with `Floor{Calibrated: true}` carries a `detail` string that contradicts its own `floor.calibrated`, and §4 above requires that string be rendered verbatim. The console would render a contradiction and a test would pin it.

So the conditionality is proven **at the component, from a hand-built prop**, not from an emitted payload: `<Refusal>` is rendered directly with `floor={{value: 0.35, calibrated: true, applicable: true}}` and a `detail` the test supplies. That is a unit test of the console's own branch and it is honest about being one. The emitted `ask-refused-below-floor.json` stays uncalibrated, because uncalibrated is the only thing the gateway can currently produce. The gateway-side defect is recorded as a contradiction below; it belongs to P6.

### 3. The citation is the product; the permalink is a convenience that is sometimes absent.

Spec:219–223 — the tuple is `(repo, commit, path, startLine, endLine, digest)`, "rendered as a forge permalink … which is immutable by construction", and "**Digest** proves the retrieved text is the indexed text". `cite.go:13–19` says it in the code: "The tuple is the claim and the permalink is a convenience: Digest is what keeps the claim checkable when the link cannot be rendered."

**When there is no link — read from the code, not guessed.** `Permalink` (`cite.go:179–186`) re-admits the remote through `forgePolicy`, whose host set is the `forges` table (`cite.go:149–152`) — **`github.com` and `codeberg.org` only** — and returns `""` on any failure. `admit.DefaultHosts` is the same two (`admit.go:53`) but `ALLOWED_HOSTS` replaces that list wholesale (`apps/gateway/cmd/main.go:100–102`). So an operator who allowlists a third forge gets a corpus every one of whose citations has `permalink: ""`, and `cite.go:157–161` says why the two sets are deliberately different: "whose URL shape do we know is a different question from whose code may we clone".

There is a **second** absence, and it is a different fact: `callerView.Citation` and `approximateCallerView.Citation` are `*rag.Citation` (`graph.go:81`, `graph.go:91`) and are `null` when the definition has no span at all (`graph.go:342–345`) — a declaration longer than one window. That is "no digest exists", not "no link exists".

**What this plan does.** Three renderings, never two:
- **link + tuple** — the `<a href>` is the `permalink` string **verbatim from the payload**, never constructed;
- **tuple, no link, and a reason** — the tuple is rendered in full, with a `git show`-shaped check the reader can run, and a sentence saying codetrail does not know this forge's URL shape;
- **location, no digest** — for a symbol with no span: path and line range from the symbol row itself (`symbolView.path`, `start_line`, `end_line`), and a sentence saying there is no digest to check.

Hiding the tuple when the link is missing, and rendering `href=""`, are both forbidden, and Task 3 kills both.

### 4. Staleness is a **specific sentence the server wrote**. The client may render it and may not compose one.

Spec:224–226 — "**Staleness is explicit.** If the ref has moved since indexing, the API says the citation is from an older commit. 'Correct at commit X, and X is three months behind `main`' is a different claim from 'correct'." `cite.go:100–115` renders that as a `Note` in two shapes, and the unknown-state one is, verbatim:

```
Correct at commit %s, indexed %s ago. codetrail has not checked whether %s has moved since.
```

That last clause is a *negative claim about codetrail's own knowledge*. "May be out of date" is a claim about the code, which nobody made and nothing checked. `Staleness.ForgeChecked` exists on the wire "so it stops Note being read as a freshness guarantee" (`cite.go:36–40`).

**What this plan does.** `staleness.note` is rendered verbatim, from the payload, in one component. The console composes no sentence from `indexed_at`, `commit` or `ref`. Task 3 asserts the exact substring **and** asserts that no paraphrase (`/may be out of date|possibly stale|might have changed|last updated/i`) appears anywhere in the tree — because a mutant that renders both the note and a paraphrase escapes a positive-only assertion.

### 5. An admission rejection names **which rule** failed.

Spec:258 — "Admission rejection → `400` naming **which rule** failed, never a generic refusal." `handler.go:146–165` honours it: `{"error": ae.Detail, "rule": ae.Rule}` with `Rule ∈ {form, scheme, host}` (`admit.go:18–22`) and details like `scheme "http"; only https is accepted`, `example.com is not an allowed host`, `path must be /owner/name` — plus a fourth the route adds itself, `ref must be a plain git ref name` (`handler.go:160–165`), which reuses `rule: "form"`. **So `rule` is a category and `detail` is the message**, and several details share one rule. Rendering `rule` would be a generic refusal wearing a label.

**What this plan does.** The console renders the server's `detail` string, never a message of its own. It also does **not pre-validate the remote**: a client-side allowlist would diverge from `ALLOWED_HOSTS`, which is deployment configuration the browser cannot see, and would refuse a URL the deployment accepts — with a different sentence, from a rule nobody can name. The only client-side check on the remote is non-empty, because an empty submit is a request that cannot succeed and there is no rule to learn from it. Task 4's mutation is the client-side `https` check, and it is killed by asserting that the request *was made*.

## Global Constraints

- Go **1.27**; module `github.com/mralaminahamed/codetrail`. Node **22 LTS** for the console.
- Default branch is **`trunk`**. Branch from it, one PR per task, **merge commits, never squash**. Never `--no-verify`.
- Commit author **and** committer must be `Al Amin Ahamed <alamin.ahamed.dev@gmail.com>`. A pre-push hook enforces it; `core.hooksPath` is `../.githooks`, so the script resolves to `.githooks/pre-push` beside the repository root. Do not bypass it.
- Comments are **minimal and short** — say *why*, never restate *what*. This applies to TSX as much as to Go; a comment restating a JSX attribute is noise, a comment saying why the region is `role="status"` and not `role="alert"` is the only record of a decision.
- **Conventional Commits, one scope per commit, small.** The scope for this phase is `console` for everything under `apps/console`, `gateway` for the fixture emitter, `ci` for the workflow.
- **React 19 + TypeScript + Tailwind v4** (spec:42). TypeScript runs `strict` with `noUncheckedIndexedAccess`; a parser that indexes an array without proving the element exists is exactly the code this phase must not ship.
- **CI is `.github/workflows/ci.yml`.** The console gets its **own job**, in the same file, in the same style (actions pinned by commit SHA, comments explaining what a green run proves and what it cannot). It declares no `services:` and no `needs:`, so it runs **in parallel with `go`** and the Go job's wall clock is unchanged.
- **No CORS middleware is added to the gateway in this phase.** Verified: `server.New` mounts exactly three middlewares — `Recover`, `RequestID` and `BodyLimit` — and then `health.Register` (`server.go:14–22`), and a repository-wide `grep -rni "cors\|access-control"` returns nothing. Adding `Access-Control-Allow-Origin` to an unauthenticated public API that accepts a stranger's URL and runs `git clone` would let any page on the internet drive ingestion from a visitor's browser, and no line of the console needs it. The console is **same-origin in every environment**: Vite's dev and preview proxies in development, and a single origin in front of both processes in P8.
- **The console never talks to a host it was compiled with.** The API base is the relative prefix `/api`, and there is no `VITE_API_URL`. A base URL in the bundle is a bundle per environment and a CORS requirement smuggled in through configuration.
- **No Go source changes.** The phase adds exactly one Go file, `apps/gateway/internal/handler/fixtures_live_test.go`, behind `//go:build live`. It contains the two stub `Retriever`s Task 2 needs, and those stubs supply a `rag.Result` and never a JSON body — the fixture still comes out of the shipped response structs. If a task finds itself editing a handler, the API shape is wrong and that is an Open question, not an edit. **Two such findings surfaced while this plan was written and both are filed rather than fixed:** `detail()`'s unconditional calibration disclaimer, and `Assemble`'s unreachable missing-span branch. Both are in the tensions section.
- **`gofmt -l apps packages` must stay empty and `go vet ./...` clean — and the reason they do is not the one you would guess. Measured on go1.27.0, in a throwaway module:**

  ```
  $ gofmt -l apps                    # with a stray .go file under apps/console/node_modules
  apps/console/node_modules/bad.go
  $ go list ./...
  probe/apps/console
  probe/apps/console/node_modules
  probe/apps/console/node_modules/somepkg
  ```

  **`gofmt` walks `node_modules`, and so does `./...`.** The frequently repeated claim that the go command skips a directory named `node_modules` did not hold here, and this plan asserted it in an earlier draft. What actually keeps CI green is the *job separation*: the `go` job never runs `npm ci`, so `node_modules` is not on that runner's disk at all, and the `console` job never runs a Go command. CI's `gofmt` step therefore stays byte-identical and is provably unaffected.

  Locally it **is** affected, after a developer runs `npm ci`. So the `Makefile`'s `lint` target scopes gofmt by tracked files rather than by directory:

  ```make
  GOFILES := $(shell git ls-files '*.go')
  ```

  `go vet ./...` has no equivalent scoping and stays exposed to a dependency that ships Go source. **Task 1 measures it** — `npm ci && go list ./... | grep node_modules | wc -l` — and records the count. Zero today is a measurement, not a guarantee; if a future dependency makes it non-zero the fix is a scoped package pattern in the `Makefile`, not a weakened check, and not moving `apps/console` (spec:42 names the path).
- **The `Makefile` gets `console-lint` and `console-test` targets, and `lint`/`test` depend on them.** Without this, `make lint` and `make test` silently skip the console — a developer's green local run would say nothing about half the phase. P6 and P8 both extend this file too; keep the additions to two named targets and two prerequisites so a three-way merge is trivial.
- **The corpus is untrusted content.** `span.text`, `answer`, `symbol.name`, `path` and `remote` all come from a stranger's repository through a public endpoint. React escapes text by default; nothing in this phase may use `dangerouslySetInnerHTML`, and nothing may put a corpus string into an `href`, a `src` or a `style`. The one URL the console renders is `citation.permalink`, and it was generated by `cite.go` from an admitted host — Task 3 still asserts it starts with `https://` before rendering it as a link, because a `javascript:` href is one bad `forges` entry away and the assertion costs one line.

## How to mutate, and what counts as a kill

P1–P4 ran roughly 450 mutations. *(Corrected 2026-09-06: this sentence said "roughly 380". P5, P6 and P7 each gave a different figure — 380, 450 and 480 — for the same P1–P4 population, in the same sentence, on the same date. 450 is the defensible one; all three now say it.)* The audit found ~30 predicted failure messages wrong, **nine false rationales** — where the plan's stated reason for the code was wrong, so the mutation derived from it proved nothing about anything — several void mutations, and the structural finding that **per-task rounds are not enough**: P3's and P4's per-task rounds each closed with "no survivors" and each whole-branch sweep afterwards found more, every one of them one of two shapes:

- **(a) a side effect nothing reads back**, and
- **(b) an error branch behind a fake nobody wired.**

**A UI adds a third shape, and it is the one that will cost this phase its budget if it is not named up front: (c) a fixture that discriminates while the *assertion* does not.** `getByRole("heading")` finding *something* is not evidence that the right thing rendered. `getByText(/floor/)` passes for a paragraph that says the floor is calibrated. `expect(link).toBeInTheDocument()` passes for a link to the wrong commit. **Every assertion in this phase must be paired with a sentence saying what a mutant would have to do to escape it**, and where the answer is "render anything at all", the assertion is rewritten until the answer is "produce this exact string / this exact href / this exact absence".

The rules, carried from P4 and adapted where the language changes them:

1. **Commit before you mutate.** `git status --porcelain` empty before the first edit; `git checkout -- <file>` restores from `HEAD`.
2. **The mutant must typecheck and lint.** `npx tsc --noEmit && npm run lint` after applying it. Void kills, each of which has already happened at least once in this project in its Go form: a mutant that only breaks the build proves nothing; a mutant in unreachable code proves nothing; **a mutant that makes React throw during `render()` is an incident, not a kill** — the test fails at the render call, before its own claim is evaluated, and the message names a stack rather than a behaviour. Where a mutation would crash a component, apply it one layer down, at the parser, and assert the *value*.
3. **Predicted output is an expectation, not a fact.** Every block below says what the failure is *expected* to look like. Run it, **paste the observed output into the plan**, correct the prediction. A block still reading as a prediction when the task is done is an unfinished task.
4. **Name the fixture that separates mutant from original, and say why it can.** See the fixture rules below.
5. **State the rationale for the code you are mutating, and verify it against the real code.** Nine false rationales have shipped in this project. Every rationale in this document that concerns the gateway carries a `file:line`; check it before you mutate, and if the code does not say what the block says it says, the block is wrong and the mutation proves nothing.
6. **If you cannot describe the failing output, the test is not evidence.**
7. **A kill is an assertion failing.** A thrown render, an unhandled promise rejection, a fake-timer deadlock or an MSW "no handler for this request" is an incident. Fix the test so its own claim is what fails, then re-run.
8. **Assert the discriminating property, not a proxy.** Assert the *exact href*, not that a link exists. Assert the *reason*, not that a refusal happened. Assert the *role*, and the absence of the other role. Assert *which* rule's detail, and the absence of the other two.
9. **A comment claiming safety is the highest-risk line in the file.** Run the counterfactual, paste the output into the commit message, then write the comment. If the counterfactual passes, the claim is false — delete it.

Format, unchanged from P4 except for the last two lines:

```
**M<n> — <one-line description of the edit>.**
- *Why the code exists:* <the rationale a reviewer can disagree with>
- *Fixture that separates mutant from original:* <which fixture, and why it can>
- *Must fail:* <test name>
- *Expected (verify and correct):* <message>
- *Typechecks and lints:* <why the mutant is a behaviour change, not a build break>
- *How a mutant could still escape this assertion:* <and why it cannot>
```

## Fixtures that can tell a console bug from a passing test

Six rules. The first four are this phase's; the last two are P3's and P4's, restated because they apply unchanged to a client.

1. **A fixture from one forge cannot detect a client-side permalink constructor.** A console that builds `remote + "/blob/" + commit + "/" + path + "#L…"` is byte-identical to the server's answer for every GitHub repository in existence. Every citation fixture set contains **a `codeberg.org` citation**, whose real permalink is `/src/commit/<sha>/…` (`cite.go:151`), and **a citation with `permalink: ""`** from an operator-allowlisted third host. The GitHub fixture alone can prove nothing about where the string came from.
2. **A fixture where every citation has a digest cannot detect the null-citation path.** `callerView.Citation` is a pointer (`graph.go:81`). Every callers fixture contains **at least one caller row whose `citation` is `null`**, and the assertion names that row's path and line range — not a count, since a count survives a mutant that drops the row entirely.
3. **A fixture with one refusal reason cannot detect a collapsed refusal renderer.** `detail()` (`read.go:386–398`) writes three different sentences for `no_spans`, `below_floor` and `unscored`. Every refusal test uses **all three**, and asserts each one's own sentence *and* the absence of the other two — a mutant that renders a single "no answer" string passes a one-reason fixture.
4. **A test with real timers cannot detect a polling-policy bug, and a test with fake timers can deadlock instead of failing.** Every poller test uses `vi.useFakeTimers()`, drives time with `await vi.advanceTimersByTimeAsync(ms)`, and asserts **the number and the spacing of the requests MSW saw** — not that "polling happened". A test that asserts only "eventually done" passes under every interval, every ceiling and every backoff.
5. **Every list fixture holds two of the thing** (P3 rule 3, P4 rule 5, unchanged in spirit). Two repos in the corpus listing, two definitions for one name, two callers on two spans, two hits. A single-element list makes ordering, keying and per-row rendering unobservable, and a mutant that renders `rows[0]` for every row passes it.
6. **The expected order must disagree with insertion order and with alphabetical order.** The API's order is the API's claim — `ListRepos` is most-recently-used first, `ORDER BY last_queried_at DESC, id` (`packages/shared/store/read.go:36`; note that a bare `read.go` everywhere else in this plan means the *handler's*), search hits are fused rank order. The console must render the order it was given and must not sort. Fixtures are constructed so that server order, alphabetical order and array-index order are three different orders, and the assertion is on the rendered sequence.

One more, from the shape of this phase rather than from a rule: **a fixture nobody generated from the real gateway is a guess that typechecks.** Task 2 emits every fixture from the shipped handlers over a live Postgres and CI fails when a committed fixture differs from what the handlers now produce. What that buys and what it does not is stated there.

## What P5 carries forward: the API as it actually is

Every field below was read out of the shipped code, not out of the spec. **Routes are mounted under `/api`** (`handler.go:43`) — the phase brief listed them unprefixed, and they are not.

| Route | Success | Failure |
| --- | --- | --- |
| `POST /api/repos` | `202` `{id, remote, ref, status, repo_id?}` | `400 {error, rule}` with `rule ∈ form\|scheme\|host` |
| `GET /api/jobs/:id` | `200` same shape | `404 {error:"no such job"}`, `500 {error, request_id}` |
| `GET /api/repos?limit=` | `200 {repos:[{id,remote,ref,commit,indexed_at,last_used_at}], count}` | `400` on `limit` outside 1..50 |
| `GET /api/repos/:repo` | `200 {id,remote,ref,commit,indexed_at,files,spans,files_with_spans,symbols,edges,edges_resolved,edges_syntactic,staleness}` | `404`, `410` |
| `GET /api/repos/:repo/spans/:span` | `200 {span:{id,path,kind,symbol,start_line,end_line,text}, citation}` | `404`, `410` |
| `POST /api/repos/:repo/search` | `200 {repo_id,mode,top_score,count,hits[]}` | `400`, `404`, `410`, `500` |
| `POST /api/repos/:repo/ask` | `200` **two shapes**, see below | `400`, `404`, `410`, `500` |
| `GET /api/repos/:repo/symbols?name=&pkg=&suffix=&limit=` | `200 {repo_id,count,matched,truncated,symbols[],staleness}` | `400`, `404`, `410` |
| `GET /api/repos/:repo/symbols/:symbol` | `200 {symbol, citation, staleness}` | `404`, `410` |
| `GET /api/repos/:repo/symbols/:symbol/callers?depth=&limit=` | `200 {repo_id,symbol,depth,truncated,callers[],approximate{}}` | `400`, `404`, `410` |

Ten facts about it that the console has to be built around, each verified:

- **`ask` returns two different objects under one status.** Answered (`read.go:148–160`): `{repo_id, refused:false, answered_by:"extractive", answer, citations, dropped, mode, top_score, floor}`. Refused (`read.go:166–174`): `{repo_id, refused:true, reason, detail, mode, top_score, floor}` — **no `answer`, no `citations`, no `dropped`, no `answered_by`.** The discriminant is `refused`.
- **`citations` is the only array in this API that can serialise as `null`.** `Assemble` builds it with `append` from a nil slice (`answer.go:99–105`), and every other list route allocates with `make(…, 0, …)`. An answered response where every hit's span failed to travel is `{"answer":"", "citations":null, "dropped":N}` — representable, and a `.map` on it throws. The parser normalises it to `[]` and Task 2 pins that as a value.
- **`top_score` and `hit.vector_score` are nullable and `null` is not `0`.** `number()` returns nil for NaN (`read.go:555–560`) and `vectorScore` returns nil when the vector arm did not return the span (`read.go:545–550`). Rendering `null` as `0` claims a similarity of zero, which is a real and much worse similarity than "unknown".
- **`floor` travels on both ask shapes and on neither search shape.** `read.go:313–314`: "No floor on this route. Search ranks; the floor is the answer's decision, and reporting one here would imply a filter that did not run."
- **`floor.applicable` is `out.VectorRan`** (`read.go:346`) — false in lexical-only mode, where there is no cosine similarity for a floor to be about.
- **`answered_by` is the constant `"extractive"`** (`read.go:70`), present so a client written now can notice P7's silent downgrade. The console renders it; it does not hide it because there is only one value today.
- **`mode` may not be sent.** `read.go:452–455` refuses the field outright — *every* value, including the configured one. The request body has exactly `q` and optionally `limit`.
- **`limit` is 1..50 or a `400`** (`read.go:59`, `read.go:474–477`), and `q` is 1..1000 characters and must contain a letter or digit (`read.go:461–468`). `depth` is 1..5 or a `400` (`graph.go:30`, `graph.go:362–372`), never clamped.
- **`404` vs `410` is decided in one place** (`read.go:410–433`) and the bodies differ in words: `"no such repository"` against `"this repository was indexed and has since been evicted"`.
- **`rule` is only a discriminator on `POST /api/repos`.** Every other 400 in the API goes through `badRequest`, which hard-codes `string(admit.RuleForm)` (`read.go:497–500`). So the console renders `error` — the detail — everywhere, and `rule` only where it distinguishes.

And the one thing the API **does not** carry, which this phase is the first to feel:

- **A failed job does not say why.** `jobView` (`handler.go:84–90`) projects `id, remote, ref, status, repo_id` and deliberately drops `attempts` and `error`. The comment at `handler.go:75–78` is explicit: *"Spec §10 wants a terminal failure to carry its reason into the API. That is deliberately not honoured yet: no safe vocabulary for a reason exists today, and git's stderr is not one. Surfacing nothing beats surfacing a path. Do not close this gap by piping the raw column through."* This is a **direct contradiction with spec:261 and spec:137**, it is recorded below, and P5 does not resolve it in code.

- **No schema validation library.** The parse layer's decisions — `citations ?? ### Task 2: the typed client, the outcome taxonomy, and fixtures that cannot drift

This is the task the phase's honesty rests on. It is also the only task that writes Go.

**Files:**
- Create: `apps/console/src/api/http.ts`, `apps/console/src/api/types.ts`, `apps/console/src/api/parse.ts`, `apps/console/src/api/client.ts`, `apps/console/src/test/msw.ts`, `apps/console/src/api/fixtures/*.json`

- Test: `apps/console/src/api/http.test.ts`, `apps/console/src/api/parse.test.ts`, `apps/console/src/api/client.test.ts`

**Interfaces:**
- `Outcome<T>` exactly as given in "What the spec decides" §1.
- `AskResult = Answered | Refused`, discriminated on `refused`.
- `get<T>(path, parse)` / `post<T>(path, body, parse)` — the only two functions that call `fetch`.
- Named endpoint functions: `submitRepo`, `getJob`, `listRepos`, `getRepo`, `getSpan`, `search`, `ask`, `listSymbols`, `getSymbol`, `callersOf`.

**Decisions, with their reasoning:**

- **A refusal is not in `Outcome`.** Stated above; it is the phase's central type decision. `ask()` returns `Outcome<AskResult>` and `AskResult` is a union on `refused`. Rendering a refusal through the error path therefore requires writing `{kind:"failed"}` deliberately, which is M1.
- **`unreachable` is separate from `failed`.** A `fetch` that rejects is a browser, a network or a dead process; a `500` is the gateway saying it broke and handing back a request id (`handler.go:193–197`). They need different words and different affordances — "codetrail could not be reached, retrying" against "codetrail failed; quote request id X" — and one union member for both would put a retry button on an internal error and a request id on a dropped Wi-Fi connection.
- **The parser normalises exactly four things, and each is a line a mutation can target.** `citations ?? []`; `top_score`/`vector_score` stay `number | null` and are never coerced; `permalink` stays `""` and is never turned into a URL; `citation` on caller rows stays `Citation | null`. Nothing else is normalised — a field the parser silently defaults is a field whose absence nobody will ever notice.
- **The parser is total and returns `Outcome`, never throws.** A malformed body from a proxy or a captive portal is `{kind:"failed"}` with a request id of `null`, not an exception that unmounts the tree. `fetch` on a `text/html` error page is a real production shape and it must render as an error, not as a white screen.
- **Fixtures are emitted from the shipped handlers wherever the shipped code path can reach them.** A hand-written fixture is a guess about the API that typechecks against a hand-written type — two guesses agreeing with each other. `fixtures_live_test.go` drives the real `handler.Handler` over a live Postgres seeded with a known corpus, writes each response body to `apps/console/src/api/fixtures/`, and **fails when a committed fixture differs**. CI's existing live step then fails on a handler shape change that the console has not been updated for.
- **Every time-valued field in a fixture is seeded, never normalised away.** The handler has one seam and it is not enough on its own. `Handler.Now` is a field, and its comment says why — *"A field so a test can pin the staleness wording against a fixed clock"* (`handler.go:36–38`) — so it pins `now` in every citation and staleness note. It does **not** pin the row: `TouchRepo` writes `last_queried_at = now()` in SQL (`packages/shared/store/repos.go:141`), and `PutRepo` stamps `indexed_at` the same way, both from the *database's* clock, which no Go field reaches. So the emitter does two things, not one: it sets `Handler.Now` to a literal, **and** it `UPDATE`s `repos.indexed_at` / `repos.last_queried_at` to literals immediately before each emit, after any handler call that would have touched them. Normalising a timestamp out of a fixture afterwards would let the staleness sentence — the thing Task 3 pins verbatim — drift without the guard noticing, which is the one drift this guard exists to catch.
- **Three levels of reachability, and the emitter labels every fixture with which one it is.** This matters more than it looks: a fixture the shipped stack cannot produce is a fixture the guard cannot guard, and calling it "emitted" would be the plan lying about its own evidence.

  **(a) Emitted through the real `*rag.Retriever`** — the default, and everything not named below.

  **(b) Emitted through the real `handler.Handler` with a stub `Retriever`.** `Handler.Rag` is an interface for exactly this reason (`read.go:42–49`: "the outcomes this handler has to tell apart … are properties of a result, not of a query anyone can write"). Two fixtures need it, and neither is reachable otherwise:

  - **`ask-answered-empty.json`** — the `citations: null` shape. `Assemble`'s "the span did not travel" branch (`answer.go:83–89`) is **dead code under the real retriever**: `spansOf` builds its `want` set from the very hits it is called with and fills `out` from the same arms (`packages/shared/rag/retrieve.go:190–203`, called as `spansOf(res.Hits, vector, lexical)` at `retrieve.go:124`), so `spans[h.SpanID]` is present for every hit, always. A stub returning `Result{Hits: […], Spans: {}}` is the only way to reach it. **This is itself a finding worth recording:** the branch is unreachable today, and a P7 tool loop that assembles from hits it did not retrieve alongside is exactly how it stops being.
  - **`ask-refused-unscored.json`** — needs `math.IsNaN(top)` with `VectorRan` true (`decide.go:83–84`). The real retriever sets `TopScore = math.NaN()` only before the vector arm runs, and `VectorRan` is `r.Mode != ModeLexical` (`retrieve.go:92`), so the pair is unproducible from a query. The handler suite already reaches it exactly once, with a hand-built result, at `read_test.go:1257`.

  Both stubs are *fakes of one interface the production code declares*, not rewrites of the handler, so the fixture still comes out of the shipped response structs and the shipped `detail()`/`floorView` logic. That is the line: a stub may supply a `rag.Result`, never a JSON body.

  **(c) Hand-written literals, each carrying a comment naming why it cannot be emitted.** Exactly one:

  - **a citation whose `permalink` is not `https:`** — the defensive check at Task 3's decision list. `Permalink` re-admits the remote through `admit.Check` (`cite.go:180–183`), which refuses any non-`https` scheme (`admit/admit.go:77–78`), so no configuration of the shipped code produces one. The fixture exists to prove the console's guard is wired, and its comment says the guard is defence against a future `forges` entry, not against anything the code can do today.

  `permalink: ""` and `below_floor` are **not** in this category, and the difference is worth stating: both are class (a). An empty permalink is what the shipped `Permalink` returns for a host the `forges` table does not know (`cite.go:179–186`), which an operator produces with `ALLOWED_HOSTS`; a below-floor refusal is what the shipped `Decide` returns with `ANSWER_SCORE_FLOOR` set. Both are supported configurations, and the emitter's comment says which configuration each one needs.
- **Search is emitted twice, because one search response cannot carry both nullable-score shapes.** In lexical-only mode `res.VectorRan` is false (`retrieve.go:92`), no vector arm runs, **every** `Fused` has `VectorRank == 0`, and `vectorScore` therefore returns nil for every hit (`read.go:545–550`) while `top_score` stays `null`. In hybrid mode `top_score` is a number and only the spans the vector arm missed have a null `vector_score`. So "a null score beside a real one" exists only in hybrid, and "a null `top_score`" only in lexical. `search-hybrid.json` and `search-lexical.json`, and each mutation below names which one it needs.
- **No test hits a real gateway, and here is what that costs.** Every console test runs against MSW over committed fixtures. That pins the *shape* and the *content* of what the console renders; it cannot prove the browser reaches a running gateway, that the proxy is configured right, or that a preflight does what this plan expects. Task 8 closes that by hand, once, against a live gateway and a real repository — the way P4 closed its own end-to-end claim against `rs/zerolog` — and records the result rather than asserting it.

### Task 5: watch indexing — the poller, its ceiling, and what it says when a job fails

Spec:42's second verb. This is the only stateful machinery in the phase and the only place a decision about *how often* is made.

**Files:**
- Create: `apps/console/src/views/Job.tsx`, `apps/console/src/hooks/useJob.ts`, `apps/console/src/hooks/pollSchedule.ts`
- Test: `apps/console/src/hooks/pollSchedule.test.ts`, `apps/console/src/hooks/useJob.test.tsx`, `apps/console/src/views/Job.test.tsx`

**Decisions, with their reasoning:**

- **The schedule is staged on elapsed time, and it is a pure function.** `intervalFor(elapsedMs)` lives alone in `pollSchedule.ts` so it can be tested as a table with no timers at all, and so the mutation lands on a number rather than on a `useEffect`.

  | elapsed | interval |
  | --- | --- |
  | 0–15s | 1s |
  | 15s–2m | 2s |
  | 2m–10m | 5s |
  | 10m–30m | 15s |
  | ≥30m | **stop** |

  The reasoning is measured, not chosen: the README records `rs/zerolog` at about 2.5 minutes, nearly all of it embedding on CPU, so the first two minutes are where someone is actually watching and a 1–2s interval is what makes the page feel live. After ten minutes nobody is watching, and this endpoint has no auth and no rate limit (spec:145–147). Thirty minutes is the ceiling because a job that has not reached a terminal state by then is not a slow repository, it is a queue nobody is serving — a different problem, which the UI should *say* rather than poll at.
- **At the ceiling the poller stops and offers a manual "Check again".** It does not keep polling quietly and it does not claim the job failed. Words: *"Still indexing after 30 minutes. codetrail has stopped checking automatically; a repository this large is possible, and so is an indexer that is not running."*
- **A tab left open for an hour costs about 244 requests and then stops; a hidden tab costs none.** The arithmetic, written out because an earlier draft of this plan said "~200" and was wrong: `15 + 105/2 + 480/5 + 1200/15 = 15 + 52 + 96 + 80 = 243`, plus one immediate poll at `t=0` = **244**, all of them inside the first thirty minutes and none after. Implementers: the ±1 depends on two boundary choices this plan deliberately leaves to the code — whether a tick landing exactly on a stage boundary belongs to the lower stage or the upper, and whether `t=0` polls immediately. Fix both in `pollSchedule.ts`, assert the resulting count as a literal, and correct the numbers in M1 and M2 to what you measure.
  `document.hidden` pauses the poller; `visibilitychange` back to visible polls immediately and resets the *transport* backoff but **not** the elapsed clock, because elapsed time is a property of the job and not of the tab.
- **Transport failure has its own backoff: 1, 2, 4, 8, 16, 30s, then 30s, and after 10 consecutive failures it stops.** No jitter — there is one browser tab, not a thundering herd, and jitter would force every test to assert a range instead of a value.
- **A `404` is terminal and immediate.** A job id that does not exist will not start existing. Retrying it is a loop that cannot succeed, and the message says the job is unknown, not that codetrail is down.
- **`failed` stops polling and says, in these words, that the reason is not available:** *"Indexing failed. codetrail does not report why a job failed: the gateway deliberately withholds the indexer's stderr, which has carried filesystem paths and credential-bearing URLs."* This is not a UI choice — it is `handler.go:75–78` — and it is the phase's most visible spec contradiction (recorded below). Softening it to "something went wrong" would hide a known gap behind a shrug.
- **`done` stops polling, announces, and renders a link to the repository built from `repo_id`.** It does **not** move focus (Task 1's rule: a poll never steals focus), and the link is the first focusable element in the newly revealed region so a keyboard user's next `Tab` lands on it.
- **The live region's text is a function of `status` alone.** Four sentences, one per status. It must not contain a counter, a timestamp or an elapsed time, because a live region whose text changes on every poll re-announces on every poll.

- [ ] **The poller has a stated schedule, a hard ceiling, a visibility pause, a transport backoff and three different responses to 404, 5xx and a dead network**, each with its own test and its own mutation. A tab left open for an hour issues bounded requests; a hidden tab issues none.
- [ ] **A poll never moves focus**, proven by an `activeElement` assertion across a status change.
- [ ] **Accessibility is in the tasks, not in a follow-up.** Skip link, landmarks, one `h1` per view, focus on navigation only, a polite single live region whose text is a function of status, provenance in words rather than colour, a list that is a list, and keyboard tests beside every axe run — with the plan stating that axe is a floor and not the claim.
- [ ] **The console is same-origin by construction and the gateway gained no CORS middleware.** The API base is relative and there is no environment-specific bundle.
- [ ] **The console's fixtures are emitted from the shipped handlers wherever the shipped code path reaches them, and cannot drift**, guarded by the existing live CI step. The three that the stack cannot produce — two needing a stub `Retriever`, one hand-written — are labelled as such beside the files, so the guard's coverage is legible instead of assumed.
- [ ] **The console's CI job runs in parallel with `go` and the Go job is unchanged**, and `make lint` / `make test` cover the console rather than skipping it.
- [ ] Every mutation recorded with observed output; every survivor recorded as a survivor with what it revealed; the whole-branch sweep run after the last merge.

**Not in P5, deliberately:** no CORS middleware and no static serving from the gateway — P8 puts one origin in front of both. No LLM answering — §8's opt-in loop is P7, and `answered_by` is rendered today so that its arrival is visible. No eval numbers, no calibrated floor — P6. No incremental re-index, no graph diffing across commits. No authentication, no rate limiting, no per-user state: spec:29 says codetrail is not multi-tenant, and a console that invented a session would be inventing a product decision. No job-history browsing: what a caller may still poll for is a server-side retention question (spec:318–321) that P5 may not answer.

## Open questions

Nothing here is blocking. Each is something the spec does not settle, with the tradeoff and a recommendation, so a reviewer can disagree with a decision rather than discover it.

1. **How a user gets back to a job.** There is no endpoint that lists jobs, `jobView` is the only projection, and a re-submission after completion creates a new row rather than returning the old one (spec:145–149).
   *Recommendation:* keep the last few job ids in `localStorage`, keyed by `remote@ref`, and say in the README that this is browser-local and lost with the profile. The alternative — a `GET /api/jobs` listing — is the retention decision spec:318–321 explicitly defers, and answering it inside a console phase would be answering it by accident.

2. **What the console shows for a failed job.** The API carries no reason (`handler.go:75–78`), and this is the phase where a user feels it.
   *Recommendation:* say so in those words, and do not soften it. The fix is server-side and is sketched in the contradictions section below; it is a migration plus an indexer change plus a gateway change, which is a backend phase's work and does not belong in a UI PR.

3. **Whether the console should show `attempts`.** It is in `jobs.Job` and deliberately not in `jobView` — "attempts is scheduling detail" (`handler.go:70`).
   *Recommendation:* agree with the gateway. "Attempt 2 of 3" invites a user to wait for an outcome the backoff already governs, and exposing it means exposing `MAX_ATTEMPTS` too. Revisit if a failure reason ever lands, since "failed after 3 attempts, because X" is a sentence and "attempt 2 of 3" alone is not.

4. **Whether the console should offer retrieval `mode`.** It may not be sent (`read.go:452–455`) and it *is* reported in every response.
   *Recommendation:* render the response's `mode` as a fact about the deployment, next to the floor, and offer no control. A control for a field the server refuses is the decorative-parameter defect P3 shipped once with `mode` and fixed.

5. **How much span text to render before truncating.** A span is never truncated by the server, deliberately (`answer.go:61–64`), because a digest is a claim about the whole text.
   *Recommendation:* the console may **visually collapse** a long span behind a "show all" disclosure, and must never render a truncated span **without** that control, because a reader comparing what is shown against the digest would find they disagree. The collapse is a scroll region with a real expand control, not a `max-height` with an ellipsis. Pin it: the full text is in the DOM in both states, so a screen reader and a copy-paste get everything.

6. **Whether the repo view should offer a "re-index at the current ref" button.** Submitting the same `remote@ref` again is how a user refreshes a corpus, and the console has both strings on the repo view.
   *Recommendation:* yes, and label it for what it does: *"Index this repository again at `{ref}`. If the ref has moved, this creates a second corpus at the newer commit; the old one stays until it is evicted."* That is `repo = hash(remote, commit)` (spec:87) stated in a sentence, and a button labelled "refresh" would imply a replacement that does not happen.

7. **Whether P5 should render `edges_resolved` as a ratio.** P4's Open question 13 warned about "a client treating the aggregate as the label".
   *Answered in Task 7:* four numbers and a sentence, never a percentage badge. A badge is read as a quality score; the numbers are read as counts, which is what they are.

8. **Whether `?suffix=` belongs in the UI.** P4's Open question 11 deferred it "to P5 when the console knows what a user actually types".
   *Answered in Task 7:* yes, as a labelled opt-in checkbox, with the response's `matched` field rendered beside the results so a widening is visible in the answer. What is still not known is whether users reach for it; that needs a deployment, which is P8.

9. **Whether the console should be served by the gateway.** Decided: no, and the reasoning is in Global Constraints — a static route in the gateway is a filesystem or an `embed` dependency in the process spec §2 describes as the public trust boundary with steady memory, and P8 already owns putting one origin in front of two processes.
   *Revisit if* P8 finds that a single-origin deployment is harder than a static route. The cost of changing course is small: the bundle is a directory of files either way.

10. **Whether the console needs a "verify this citation" affordance beyond printing the command.** The console could fetch the forge and diff, which is exactly the egress P1 confined to the indexer, or hash the text it was given, which proves nothing about the file on disk.
    *Recommendation:* print the command and the expected digest, and nothing more. A "verified ✓" the console computed from its own copy is a tautology wearing a checkmark, and it is the most tempting wrong feature in this phase.

## What the spec leaves underspecified or in tension

Recorded so a reviewer sees them as findings rather than as choices made quietly. Two of these are outright contradictions between the spec and the shipped code.

- **CONTRADICTION — §10 and §4 say a terminal job failure carries its reason into the API; the gateway deliberately does not.** Spec:261 — "Job failure → capped attempts, backoff, terminal state carrying its reason into the API" — and spec:137 says the same. Against that, `handler.go:75–78`: *"Spec §10 wants a terminal failure to carry its reason into the API. That is deliberately not honoured yet: no safe vocabulary for a reason exists today, and git's stderr is not one. Surfacing nothing beats surfacing a path. Do not close this gap by piping the raw column through."* Both are right about their own concern: the spec is right that a failure with no reason is a dead end, and the code is right that the `jobs.error` column has carried a server filesystem path and a credential-bearing URL.
  **Proposed resolution, and it is not P5's to ship.** Add a `reason` column to `jobs` from a closed set the *indexer* assigns where it already classifies the failure — `admission`, `clone_failed`, `not_found`, `too_large`, `too_many_files`, `deadline`, `internal` — project it into `jobView` beside `status`, and leave `error` withheld. That is a migration, an indexer change and a gateway change: three scopes, none of them a console. **P5 renders the gap in words instead**, and the README says the gap is deliberate and where it is recorded. Closing it inside a UI phase would mean putting a schema migration in a UI PR, which is how a plan loses the ability to say what a phase did.

- **CONTRADICTION — §8 makes the floor the mechanism that produces refusals; the shipped default makes that mechanism inert.** Spec:230–231 — "a refusal when the top score falls under a floor that the eval measures rather than picks" — against `decide.go:25`, where `DefaultFloor()` is `-1`, and `decide.go:87`, where the test is `top < f.Value`. A cosine similarity is never below `-1`, so **`below_floor` is unreachable in a default deployment**. Spec:315 is what makes this defensible — the value is P6's — but the consequence is not written down anywhere: the refusal §8 describes as the main event is, today, the one refusal nobody will see.
  *Resolution in this plan:* the console never implies the floor filtered anything; the `below_floor` fixture is emitted with a configured floor and the emitter's comment says which configuration produces it; and the README states that at the shipped default the reachable refusals are `no_spans` and `unscored`.

- **CONTRADICTION — the below-floor refusal's own text says the floor is uncalibrated, whatever `floor.calibrated` says, and P6 turns that into a lie.** `read.go:390–393` builds the `ReasonBelowFloor` detail as `"The best match scored under the configured floor of " + <value> + ". That floor is not calibrated; its value is measured in P6."` — **unconditionally**. It never reads `f.Calibrated`, even though `floorView.Calibrated` sits beside it in the same response (`read.go:109–113`) and exists precisely so "a reader can otherwise tell a placeholder from a measurement" (`read.go:102–104`). Today the two agree by accident, because `DefaultFloor()` is uncalibrated (`decide.go:25`) and an operator's own `ANSWER_SCORE_FLOOR` is still not a number codetrail measured (`main.go:234–236`). **P6 is the phase that breaks it:** calibrating the floor means shipping `Floor{Calibrated: true}`, and this sentence then tells every user that the measured floor was never measured.
  *Resolution, and it is P6's:* `detail()` takes the flag it is already handed and appends the disclaimer only when `!f.Calibrated`, with the calibrated branch naming what it was measured from. **P5 must not fix it** — it is a one-line change in a file this phase has committed to not touching, and a UI phase editing an answer's prose is how the two stop being reviewable apart. *Consequence for this phase, stated so it is not discovered:* the console's calibrated-floor branch cannot be exercised against any payload the gateway can emit, so it is tested at the component with a hand-built prop and the test's name says so.

- **§2 promises "jump to source" and §8 makes the permalink honestly absent for some repositories.** Spec:42 lists the verb; `cite.go:172–178` returns `""` for any host the `forges` table does not know, and the allowlist is configurable independently of that table (`cite.go:157–161`). The two are reconcilable — the tuple is the claim, the link is the convenience — but §2's verb read alone would have a console render a link unconditionally. Recorded because a reader of §2 alone would ship the wrong thing.

- **§10's rule vocabulary is an admission vocabulary that the read path reuses for everything.** `badRequest` hard-codes `string(admit.RuleForm)` for `q`, `limit`, `depth`, `suffix`, `name` and `mode` failures (`read.go:497–500`), so a `400` from `POST /ask` says `rule: "form"` whatever went wrong. Spec:258's clause is about admission, so this is not a violation — but it does mean `rule` is not a discriminator outside `POST /api/repos`, and a client that switched on it would be switching on a constant. Recorded so that the console's decision to render `error` everywhere is visibly a consequence rather than a preference.

- **The spec has no CORS story, and it needs one the moment a console exists.** §2 puts the console in a browser and the gateway behind a public trust boundary and never says whether they share an origin. The gateway has no CORS middleware today (`server.go:14–22`, verified by grep). This plan chooses same-origin and states why; P8 has to honour it, and if P8 chooses two origins then the gateway needs a CORS policy that is designed rather than discovered, on an endpoint that accepts a stranger's URL and runs `git clone`.

- **§8 says "the response names which one answered it" and the refusal shape names nobody.** `answerResponse` carries `answered_by` and `refusalResponse` does not (`read.go:148–174`). That is arguably right — nothing answered — but it means a client cannot read `answered_by` uniformly, and a P7 refusal produced by a degraded LLM path will be indistinguishable from an extractive one. Worth a field then; not worth inventing now.

- **§11's counters have no console-side equivalent and this plan adds none.** Client-side error and refusal counts would be the only place a *user's* experience of a degraded gateway is visible, and there is no endpoint to send them to and no decision anywhere about whether codetrail collects telemetry. Recorded as absent on purpose rather than forgotten.

- **`Assemble`'s "the span did not travel" branch is dead code under the shipped retriever**, and the response shape it produces is on the wire regardless. `spansOf` builds its `want` set from the same hits it is handed and fills the map from the same arms (`packages/shared/rag/retrieve.go:190–203`, called at `retrieve.go:124`), so `spans[h.SpanID]` is present for every hit and `answer.go:83–89` never runs. That makes `{"answer":"", "citations":null}` a shape a client must handle and a shape no query can produce — which is why Task 2 reaches it with a stub. Recorded as a finding rather than a defect: the branch is defensive, it is correct, and P7's tool loop assembling from hits it did not retrieve alongside is exactly what would wake it up. Worth a `//nolint`-style note in `answer.go` saying so, in a phase allowed to edit it.

- **§13's ordering means P5 renders an API designed with no consumer**, which P4's own plan called out as a real risk. Two of P4's response-shape guesses were confirmed here (the split caller lists; `matched_on` and `failed` on the approximate block) and one gap was found: a caller row has everything it needs *except* a way to reach the caller's own callers without a second lookup, since `callerView.symbol.id` is present but the console must issue a fresh request per hop. That is correct and cheap and is recorded only so the next phase knows it was looked at rather than missed.
