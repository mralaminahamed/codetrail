**Goal:** Turn four processes and a compose file into a deployment where the sandbox is a *boundary the platform enforces* rather than a claim the code makes. Two images. One Terraform stack. A CD pipeline that builds, gates, applies and then proves the thing it applied actually works. The phase's headline is not "it runs in the cloud" — it is that **the indexer's runtime is denied things by the deployment, each denial has something enforcing it, and each enforcement has a test that fails when it is removed**, and that everything provable without an AWS account is provable on every pull request.

**Architecture:** `infra/` grows `gateway.Dockerfile`, `indexer.Dockerfile`, a `prometheus/` rule set, and `terraform/` — providers, network, security groups, ECS Fargate services, an ALB, RDS PostgreSQL 17 with pgvector, Secrets Manager. `apps/indexer` gains the HTTP probe surface spec §11 has required since P0 and which P3 and P4 each recorded as missing. `packages/shared/metrics` gains the three instrument families §11 names and the code has never had — job outcomes and durations, admission rejections by reason, evictions — because you cannot alert on a counter that does not exist. `infra/policy` is a Go test package that reads `terraform show -json` output and fails when the plan opens a security group to the world, gives the indexer unrestricted egress, puts a secret in plaintext, or wires a load balancer's health check to `/health` instead of `/ready`. `.github/workflows` gains `images.yml` and `deploy.yml`, and `ci.yml` grows four steps that all run with no cloud account.

**Tech Stack:** Docker (BuildKit), `gcr.io/distroless/static-debian13:nonroot` (digest-pinned) for the gateway, `debian:trixie-slim` plus a copied Go 1.27 toolchain for the indexer, Terraform ≥ 1.6 with `hashicorp/aws ~> 6.0`, AWS ECS Fargate + ALB + RDS PostgreSQL 17 + Secrets Manager + ECR, Prometheus rules validated by `promtool`, GitHub Actions with OIDC. **No new Go dependency.** The plan-policy suite parses `tfplan.json` with `encoding/json` rather than pulling in `hashicorp/terraform-json`: the file is a documented, stable JSON schema and one map traversal is smaller than a dependency.

## What §2, §4 and §11 decide, and what this plan may therefore not do

Five clauses are load-bearing. Each has a plausible opposite that a deployment could ship without anyone noticing.

### 1. The split is a *deployment* boundary, so the two apps must not share one.

spec:48–51 — *"Splitting it makes the sandbox a deployment boundary rather than a code convention."*

The tempting deployment is the wrong one: one host, one `docker compose up`, two containers on one bridge network with one egress path, or one ECS task with two containers sharing one ENI. Every one of those puts the gateway and the indexer behind **one** set of firewall rules, and the moment that happens the sentence above becomes false again — the split is back to being a code convention, expressed in a directory layout and nothing else.

**What this plan does instead:** two ECS services, two task definitions, `awsvpc` network mode, and therefore **two ENIs and two security groups**. What is actually different between them, enumerated rather than gestured at, because the first draft of this clause claimed a difference the plan did not deliver:

| | gateway | indexer |
| --- | --- | --- |
| Ingress | the service port, from the ALB security group only | the scrape port, from the observability security group only |
| ALB target group | yes | **never** — asserted |
| Task role | none | none — and for the indexer that is a control, not a default (Task 5) |
| Egress | 443, 5432, DNS — enumerated | 443, 5432, DNS — enumerated |
| Writable filesystem | none | `/scratch` and `/tmp` only |

**The egress sets are identical, and that is a real limit on this claim rather than an oversight.** A Fargate task pulls its own image, reads its own secrets and ships its own logs through its task ENI, so the gateway needs outbound 443 exactly as much as the indexer does; there is no AWS-managed prefix list for Secrets Manager, ECR or CloudWatch Logs to scope it with. So the boundary this phase delivers is **ingress, routing, ambient credentials and writable surface — not egress**, and the enumerated-versus-`protocol = "-1"` rule shape is a control on *both* rather than a difference between them. Open question 8 costs the change that would make the egress claim true as well: interface endpoints for those three services, at which point the gateway's 443 goes to the endpoint security group and not to the internet.

That difference is a resource in the plan file, it is asserted by a test over the plan JSON, and a change that merges them fails CI. The compose file gets the same treatment as far as compose can express it (separate networks), and where compose cannot express it the plan says so rather than implying parity.

### 2. The host allowlist is the SSRF control, and the network layer cannot take over from it.

spec:128–130 — *"Host-allowlisting is the SSRF control. It does **not** defend against a hostile allowlisted forge, and codetrail claims no DNS-rebinding protection: `git` is a subprocess and cannot be handed a validating dialer."*

The tempting move is to "harden" this in Terraform: a security group, a NACL or a prefix list that only lets the indexer reach GitHub. It cannot be done honestly. `github.com` resolves into a large, changing CDN range; an IP allowlist is either stale or so wide it means nothing; and an egress proxy that terminates TLS is a second trust boundary in a project whose whole point is having few. Worse, shipping one would *imply* a control the README explicitly disclaims.

**What this plan does instead:** the deployment restricts **direction and port**, never host. The indexer may open outbound tcp/443, tcp/5432 and DNS, and nothing else — no tcp/22, no tcp/9418 (`git://`), no arbitrary high ports — and accepts inbound on nothing but the scrape port, from the scraper's security group. The *host* decision stays where §4 put it: `admit.Policy` in the process. The deployment's obligation is therefore **not to weaken it**: `ALLOWED_HOSTS` is written explicitly into the task definition as `github.com,codeberg.org`, and a policy test fails if it is absent or different, so widening the allowlist is a reviewed diff rather than a forgotten environment variable. The egress-proxy and prefix-list options are named in Open question 3 with their staleness cost, and neither is shipped.

### 3. The environment allowlist is closed *by omission*, and a container image is a second environment.

`packages/shared/symbols/policy.go:38–47` — *"Everything absent here … is closed by omission. That is deliberate and not laziness: an entry setting one of them to a safe value would still be safe under an append-to-`os.Environ` mutation, and omission is not."*

The failure this predicts is not in Go code at all. It is in a `Dockerfile` or a task definition:

- A base image built `FROM golang:1.27` keeps `GOPATH`, `GOFLAGS` and a **populated module cache** in the runtime layer. `Policy.Env()` re-points `GOMODCACHE` per job (`policy.go:99`), so the cache is unreachable — but the guarantee then comes from one line of Go rather than from the image, and nobody reading the Dockerfile can see it.
- A `GOTOOLCHAIN` or `GOFLAGS` in the image's `ENV` is invisible to the type-checker (the child environment is built from nothing) but **visible to `git`**: `apps/indexer/internal/clone/clone.go:81` is `cmd.Env = append(os.Environ(), …)`. So `HTTPS_PROXY`, `ALL_PROXY` or `GIT_*` in the task definition reach the clone even though they cannot reach the compiler. The two subprocesses have different environment disciplines and the deployment sees only one environment.
- `TYPECHECK_GOPROXY` set to anything but `off` (`apps/indexer/cmd/graph.go:286`) turns a stranger's `require` line into an outbound fetch to a host of their choosing — the SSRF §4 exists to refuse, reached by a road the allowlist cannot see, and P4 measured that road being taken.

**What this plan does instead:** the indexer's task definition environment is itself an allowlist, asserted as a whole set rather than entry by entry, exactly as `symbols.EnvKeys` (`policy.go:112–117`) is asserted in P4. The policy test enumerates the permitted variable names and **fails on any name outside the set** — so a future `HTTPS_PROXY` is a red build, not a silent re-opening. The indexer image is built from `debian:trixie-slim` with a Go toolchain copied in, not `FROM golang`, so there is no inherited `GOPATH`, no `GOFLAGS`, and no module cache anywhere in the image. **What is still baked in, because copying `/usr/local/go` copies `GOROOT/go.env` with it, is `GOPROXY=https://proxy.golang.org,direct`, `GOSUMDB` and `GOTOOLCHAIN=auto`** — closed not by omission but by `Policy.Env()`'s real environment variables outranking a defaults file (`policy.go:92–94`), which is a weaker guarantee than omission and is stated as one in Task 1.

**And there is a third environment the allowlist cannot see at all.** A task definition's `environment` block is not everything a container gets: giving the task an IAM **task role** makes ECS inject `AWS_CONTAINER_CREDENTIALS_RELATIVE_URI` at runtime and turns `169.254.170.2` into a working credential endpoint — link-local, so no security-group rule touches it — inside the process spec:41 calls the untrusted-input boundary, and `clone.Run`'s inherited environment (`clone.go:81`) carries it to `git` too. No environment assertion can catch that, because the variable is not in the artifact being asserted over. The control is to have no task role at all, which Task 5 asserts as a resource-level fact.

### 4. `/health` and `/ready` are different, and wiring them the same way is worse than wiring neither.

spec:269–271 — *"`/health` for liveness and `/ready` for dependency health, with `codetrail_ready` as a gauge — `up` says the process is listening, which a gateway that has lost Postgres still is."*

`packages/shared/health/health.go:12` answers `/health` with an unconditional `200`. `health.go:13–18` answers `/ready` from the dependency check. There are therefore two wrong wirings and they fail in opposite directions:

- **A load balancer probing `/health`** keeps a gateway in rotation that has lost Postgres and is failing every query behind a 200. This is the mistake the spec sentence was written against.
- **A container health check probing `/ready`** turns a shared-datastore outage into a rolling restart of every task. ECS replaces the task after three failures; the replacement cannot reach Postgres either; the whole service crash-loops, and the one process that could still serve `/metrics` and say *why* is the one being killed.

**What this plan does instead, and it is deliberately the opposite of the sibling project's choice** (`triagepilot/infra/terraform/ecs.tf` probes `/healthcheck` → the readiness path at the container level): **ALB target group health check → `/ready`. ECS container `healthCheck` → `/health`.** Routing follows dependency health; liveness follows the process. The policy test asserts both halves, because asserting one is how you get the other wrong. The indexer is never an ALB target, so it has only the liveness half, and its readiness exists to be scraped and alerted on, not to gate traffic.

### 5. Every ratio alert carries a minimum-traffic conjunct. State alerts carry none.

spec:274–276, quoted in full above.

The tempting implementation is `clamp_min(denominator, 0.001)`, which looks like the same thing and is not: it is a divide-by-zero guard that engages only below one event per sixteen minutes, so one errored answer out of four reads as 25% and pages. The sibling project shipped exactly that and then removed it (`triagepilot/infra/prometheus/alerts.yml`).

**What this plan does instead:** every ratio rule carries `and sum(rate(<denominator>[w])) > N / <w-in-seconds>`, written in that form so the sample size is legible in the rule itself, and **N is chosen so that the number of events that would otherwise fire the alert cannot on its own clear the threshold**. State rules — `codetrail_ready == 0`, `codetrail_score_floor_calibrated == 0`, `up == 0` — carry none, because both gauges are set at boot (`apps/gateway/cmd/main.go:60`, `:199`) and are therefore never absent while the process is scrapeable, and because one event is already the whole story. Task 3 proves the conjuncts are load-bearing with `promtool test rules`: for each ratio rule, a series at exactly the sample size that must *not* fire, and one more sample that must.

## How to verify infrastructure, and what counts as evidence

Terraform is not mutation-testable the way Go is: an HCL edit that changes behaviour usually also changes the plan JSON, so "the mutant compiles and the test still passes" is rarer and less informative. The discipline transfers anyway, in a form adapted to the artifact. Every task states, for each claim, **the artifact the claim is made about, the command that produces it, and the assertion that fails when the claim stops being true.**

The rules, adapted from P1–P4:

1. **Commit before you break anything.** `git status --porcelain` empty before the first edit; `git checkout -- <file>` restores from `HEAD`.
2. **The counterfactual must produce a plan, not an error.** A "mutation" of a Terraform file that makes `terraform validate` fail proves nothing about the assertion — it proves `validate` works. Every counterfactual in this plan is an edit that **validates and plans cleanly** and is caught only by the policy suite. Where an edit can only fail validation, it is recorded as void, exactly as a pgx protocol error was recorded as void in P4.
3. **Predicted output is an expectation, not a fact.** Every counterfactual block says what the failure looks like. Run it, **paste the observed output into the plan**, correct the prediction. A row still reading as a prediction when the task is done is an unfinished task.
4. **State the rationale for the resource you are asserting about.** Four false rationales have shipped in this project already. If the stated reason for a security-group rule is wrong, the assertion derived from it proves nothing about anything.
5. **A comment claiming safety is the highest-risk line in the file.** P2 corrected twelve false comments. This applies to HCL: `# only the ALB can reach this` beside a rule that also matches the VPC CIDR is worse than no comment, because it stops the next reader looking.
6. **An assertion over a count is weaker than an assertion over a name.** "The plan has three security groups" survives an edit that swaps which one the indexer uses. Assert `aws_security_group.indexer` by address and by rule content.
7. **A test that skips is not evidence.** The policy suite is behind `-tags=tfplan`; a missing `tfplan.json` is a **failure**, not a skip, for the reason P2's review round found two live suites that emptied a developer's database while printing `ok`.

Format for a counterfactual, matching P4's mutation format:

```
**C<n> — <the edit>.**
- *Why the resource is shaped this way:* <the rationale a reviewer can disagree with>
- *Must fail:* <test name>
- *Expected (verify and correct):* <message>
- *Plans cleanly:* <why this is a behaviour change and not a validate error>
```

## The cloud, the compute shape, and why

**Decision: AWS, ECS on Fargate, one service per app, an Application Load Balancer, and Amazon RDS for PostgreSQL 17 with pgvector.**

**The justification, against §2's actual resource profile.** spec:48–51 says the two apps have opposite profiles and that the split exists to make the sandbox a deployment boundary; the compute shape has to serve *both* halves of that sentence, and Fargate's `awsvpc` networking is the only one of the candidates that serves the first half at all — each task gets its own elastic network interface and therefore **its own security group, its own ingress, and its own ambient credentials**, so "the untrusted-input component accepts no connection, is behind no load balancer, and holds no AWS credential" is a set of resources in a plan file rather than a paragraph in a README. (What it is *not* is a difference in egress — both tasks pull an image, read a secret and ship a log through their own ENI, so both need outbound 443; the table in clause 1 says exactly which columns differ and Open question 8 costs closing the last one.) On a single EC2 host running compose, on App Runner, and on any shape where the two processes share a NIC, the boundary reverts to exactly the code convention §2 says it must not be. The second half — spiky CPU and disk against steady memory — Fargate serves by making the two task sizes independent and billing per second: the indexer gets 1 vCPU / 2 GiB and 40 GiB of ephemeral storage sized for the 256 MiB clone cap plus the go build cache, and its spike costs what the spike costs without the gateway's 0.25 vCPU / 0.5 GiB ever competing for it. Lambda is rejected not on limits but on architecture: the indexer is a *leasing loop* over a Postgres queue chosen precisely because the database was already a hard dependency (spec:53–55), and moving to Lambda means replacing that queue with an event source — changing the design to fit the compute, which is the wrong direction. EKS is rejected on price: a control plane costs more per month than every other line in the estimate below combined. EC2 with compose is the cheapest and is rejected on the first half of the sentence.

**Postgres 17 with pgvector — verified, not assumed.** Amazon RDS for PostgreSQL supports pgvector as a managed extension; RDS added pgvector **0.8.0** in November 2024 and PostgreSQL 17.10 carries **0.8.2**, per the AWS extension-versions documentation and the RDS "what's new" posts. So the answer is *not* "run it yourself": `CREATE EXTENSION IF NOT EXISTS vector` at `packages/shared/store/migrations/0001_init.sql:7` works on RDS under the master user's `rds_superuser` role, and no code change is needed. Two consequences the plan must carry rather than assume away:

- **The floor is pgvector ≥ 0.5.0, for HNSW — and the first draft's reason for putting it at 0.8.0 was backwards.** That draft argued from `apps/gateway/cmd/main.go:173–176`, which says `hnsw.iterative_scan` is off by default "so nothing compensates" for asking the index for more rows than `ef_search`. Both halves of that are true and the inference is inverted: the code *assumes no compensation*, and below 0.8.0 the GUC does not exist at all, so the assumption holds **a fortiori**. Nothing in this codebase requires 0.8.0. What genuinely requires a floor is the HNSW index the schema builds, and that is 0.5.0. Recorded as a plan defect rather than quietly renumbered, because a false rationale makes every assertion derived from it prove nothing — which is this plan's own rule 4.
- **Pin `engine_version` to a 17 minor and assert the extension version at deploy time anyway.** The assertion survives the corrected floor because its real job was never the 0.8.0 threshold: it is to catch an RDS **minor upgrade moving the extension underneath a running deployment**, which `auto_minor_version_upgrade` makes a scheduled certainty rather than a risk.
- **Dev and prod will not run the same pgvector, and prod cannot catch up.** `infra/docker-compose.yml:7` pins `pgvector/pgvector:pg17`, whose pgvector P3 recorded as **0.8.6** when it read `hnsw.ef_search`'s `boot_val` from `pg_settings` — and **0.8.2 is RDS's ceiling** (PostgreSQL 17.10), not a lagging minor that will catch up on the next patch. So the gap is structural rather than temporary. It is small and it is real, and the honest response is to make it **visible** rather than to claim parity: Task 2 adds a `codetrail_datastore_info{postgres,pgvector}` gauge read from the server at boot, and the smoke test asserts what is actually running rather than trusting it.

Aurora PostgreSQL also supports pgvector, Aurora PostgreSQL 17 is supported on Serverless v2 generally, and Serverless v2 can scale to **0 ACU** with automatic pause. What no AWS source states is whether **17 supports a 0-ACU minimum**: the supported-version list for auto-pause names 13.15+, 14.12+, 15.7+ and 16.3+ and simply stops. That is a **documentation gap, not a documented limitation** — the distinction matters, because "AWS says no" and "AWS does not say" justify different follow-ups. So "park the database at zero" is unverified rather than ruled out; it is recorded as such in the cost section and is not built.

**The one thing about this deployment that is genuinely uncomfortable, stated first rather than in a footnote.** `POST /api/repos` has no authentication and no rate limit (spec:145–149), and what it does is `git clone` a stranger's URL on your bill. The caps (`MAX_REPO_BYTES` 256 MiB, `MAX_REPO_FILES` 20000, `JOB_DEADLINE_SECONDS` 600) and LRU eviction are the *only* bounds on that, and they bound each job, not the arrival rate. Therefore `alb_allowed_cidrs` has **no default** and the plan fails without it, exactly as the sibling project's does after its own hardening round — and the variable's description says in one sentence what `["0.0.0.0/0"]` means here. `["0.0.0.0/0"]` remains a legitimate answer for a public demo; it just has to be an answer.

## Migrations and rollback

`store.New` calls `migrate()` before returning (`store.go:53–56`), so **migrations run inside the new task, at boot, before it serves anything and before ECS marks it healthy.** There is no separate migration step in this deployment and P8 must not add one: a standalone migration job would be a second migrator racing the boot-time one, and `pg_advisory_xact_lock` (`store.go:106`) exists so that race is already safe rather than so it can be reproduced in a pipeline.

Four consequences, each of which is a rule:

1. **Two services migrate, and that is fine.** Whichever of gateway and indexer boots first takes the lock; the other blocks on it, then reads the ledger through the same transaction and applies nothing. `store.go:97–106` takes the lock *before* reading the ledger precisely because deciding what to apply is half the race.
2. **During a rolling deploy the old image runs against the new schema.** ECS starts new tasks alongside old ones and drains the old ones only once the new are healthy. The new task migrates on boot; the old tasks keep serving. **Therefore every migration must be readable by the previous image.**
3. **A rollback does not un-apply a migration.** There are no down migrations, `schema_migrations` keeps the row, and ECS's `deployment_circuit_breaker` rolls back the *task definition* — the schema stays forward. The rule that follows is **expand-only**: a migration may add tables, columns, indexes and constraints that the previous image tolerates, and a destructive change ships **one release after** the code that stopped using the thing being dropped. `packages/shared/store/migrations/0006_drop_repo_status.sql` is the shape that would break this; it is safe only because nothing ever read the column, and its own comment says so. From P8 forward that is luck to be replaced with a rule — **and a rule this project recognises is an assertion, not a convention.** A comment in the migrations directory would be the highest-risk line in the file by the standard set above, and it would fail the standard this plan sets for itself: the artifact, the command that produces it, and the assertion that fails when the claim stops being true.

So Task 6 ships `make migrations-lint`, run in CI: a script over `packages/shared/store/migrations/*.sql` that fails on `DROP COLUMN`, `DROP TABLE`, `ALTER COLUMN … TYPE`, `SET NOT NULL` and `RENAME` unless the file carries an explicit `-- expand-only-exempt: <reason>` line. **`0006` is already a violation and is therefore the test's first fixture**: it takes the exemption marker, and the reason it has to write down is the one its comment already gives — the column was never read by anything, so no previous image can miss it. A rule whose first act is to make an existing file justify itself is a rule that has been run at least once.
4. **A failed migration is the good path and must stay that way.** The transaction rolls back, `store.New` returns an error, `main` calls `log.Fatal`, the container exits non-zero, ECS's circuit breaker rolls the service back to the previous task definition, and the schema is unchanged. The policy suite asserts `deployment_circuit_breaker` is enabled with `rollback = true` on every service, because without it a bad image is a crash-looping service and a green pipeline.

## The console assumption, and what P5 turned it into

**When this plan was written `apps/console` was empty and P5 was being planned in parallel.** The assumption made here was that P5 would ship a **static SPA built with Vite and served by its own image**, matching §2's description of the console as a browser app (spec:42) and the sibling project's shape. The plan was written so that either answer worked.

**P5's plan landed during this one and confirms it, and turns one preference into a requirement.** `docs/superpowers/plans/2026-09-03-p5-console.md` decides in its Open question 9 that the console is **not** served by the gateway — a static route would put a filesystem or an `embed` dependency inside the process §2 calls the public trust boundary — and its Global Constraints add the harder half: **the gateway has no CORS middleware and P5 refuses to add any**, because `Access-Control-Allow-Origin` on an unauthenticated API that runs `git clone` on a supplied URL would let any page on the internet drive ingestion from a visitor's browser. The console's API base is the relative prefix `/api` and there is no `VITE_API_URL`, so the bundle cannot be pointed anywhere.

**Therefore same-origin is not a preference P8 may trade away for a simpler load balancer.** P5's own plan says "P8 puts one origin in front of both processes" and that is now this phase's debt. Concretely:

- One ALB, one hostname, **two target groups**: a listener rule for `/api/*` → the gateway, the default action → the console. Not the sibling's nginx-proxies-`/api` arrangement — codetrail has no API key for nginx to inject, and a second target group removes the Cloud Map plus `NGINX_RESOLVER` trap the sibling hit.
- **`/health`, `/ready` and `/metrics` are not published.** P5's Vite config proxies them in development for convenience; nothing in the running console requests them. They stay reachable only by the target group health check and, for `/metrics`, by the scraper inside the VPC. Task 5 asserts that no listener rule routes them.
- Task 7 adds `infra/console.Dockerfile` and `console_enabled` flips to `true`.

`console_enabled` still defaults to **`false`**, so P8 can land before P5 without shipping a service that has no image to run. If P5's shape changes again, the only thing that must not change is the single origin.

### Task 1: Two images, and what is inside them

The images are where the sandbox stops being a Go package. Everything in `packages/shared/symbols/policy.go` assumes a filesystem, a `PATH` and a set of environment variables; this task decides all three.

**Files:**
- Create: `infra/gateway.Dockerfile`, `infra/indexer.Dockerfile`, `.dockerignore` — **corrected from `infra/.dockerignore`, which BuildKit would silently ignore with the context at the repository root. Measured: `docs/` and `assets/` were still in the context.**
- Modify: `apps/gateway/cmd/main.go` and `apps/indexer/cmd/main.go` — a `-probe` flag
- Modify: `infra/docker-compose.yml` — build both images, add a `gateway`/`indexer` service pair behind a profile
- Modify: `Makefile` — `images`, `image-test`
- Test: `infra/image_test.sh` (run by CI and by `make image-test`)

**Interfaces:**
- Produces: `codetrail/gateway` and `codetrail/indexer` images, `linux/amd64`.
- Consumes: nothing new in Go.

**Decisions, with their reasoning:**

- **The gateway is `gcr.io/distroless/static-debian13:nonroot`, pinned by digest.** A static Go binary, no shell, no package manager, uid 65532. The suffixed tag rather than the bare `static:nonroot` alias, because upstream warns that the alias currently resolves to `-debian13` and will move; an image whose base changes under a digest-free tag is a base nobody reviewed.
- **The indexer is `debian:trixie-slim` with a Go toolchain copied in, and explicitly *not* `FROM golang:1.27`.** Trixie because it is Debian stable as of 2025-08-09 and `bookworm` is oldstable — the first draft named bookworm out of habit. It must contain `git` and `go` (`README.md:540`), which rules out distroless. It must **not** carry an inherited `GOPATH`, a `GOFLAGS`, or a populated module cache, which rules out the `golang` image as a runtime base — that image ships a warm `$GOPATH/pkg/mod` and a set of `GO*` variables, and while `Policy.Env()` re-points `GOMODCACHE` per job (`policy.go:99`) so none of it is reachable, the guarantee would then live in one line of Go rather than in the artifact anyone can inspect.
- **`ca-certificates` is installed, and leaving it out would have broken every clone.** `--no-install-recommends` is right for an image this small and it drops exactly the package `git` only *Recommends*; without it `git clone https://github.com/…` (`clone.go:75`) fails TLS verification against every forge in the allowlist. It is in the install list and in `image_test.sh`, because "the image builds and the binary starts" would not have caught it. The gateway needs none: distroless static ships a CA bundle.
- **`COPY --from=golang:1.27 /usr/local/go /usr/local/go` does *not* give "a toolchain and nothing else", and the first draft said it did.** `$GOROOT/go.env` travels inside that directory carrying `GOPROXY=https://proxy.golang.org,direct`, `GOSUMDB=sum.golang.org` and `GOTOOLCHAIN=auto`. **The closure still holds**, and it is worth being exact about why: `Policy.Env()` sets real environment variables (`policy.go:92–94`), which outrank `go.env` in the go command's precedence order, so the sandbox's settings win. What is *not* true is "nothing is baked in" — `GOENV=off` (`policy.go:96`) disables the **user** env file, not `GOROOT`'s. So the honest statement is **"an explicit override wins over a baked-in default"**, which is a weaker and true claim, and one consequence follows: `GOSUMDB` is closed by omission in `EnvKeys` (`policy.go:112–117`) while `go.env` supplies a real value for it — harmless only because `GOPROXY=off` means nothing is ever fetched to check. Recorded rather than fixed, because the fix belongs in `symbols`, not in a Dockerfile.
- **`PATH` in the indexer image contains exactly one `go`.** `ENV PATH=/usr/local/go/bin:/usr/local/bin:/usr/bin:/bin`, and the image installs no Go from apt. This is load-bearing rather than tidy: `policy.go:141–147` refuses to run unless `exec.LookPath("go")` equals the configured `GoBin`, so two `go` binaries on `PATH` is a worker that logs `no_toolchain` and writes an all-syntactic graph while `go version` works perfectly from a shell.
- **Neither image sets any `GO*`, `GIT_*` or `*_PROXY` variable.** Closed by omission, mirroring `policy.go:38–47`. The image sets `HOME`, `PATH`, `SCRATCH_DIR` and `PORT`/`PROBE_PORT` and nothing else.
- **Both images carry the Amazon RDS trust store at `/etc/ssl/certs/rds-global-bundle.pem`.** Every certificate in that bundle is a self-signed Amazon RDS root; none of them chains to a publicly trusted CA, so the Mozilla store in distroless cannot validate an RDS server certificate and `sslmode=verify-full` fails at boot with an error about the certificate rather than about the setting. `ADD --chmod=644` — `ADD` writes `0600` root-owned by default and the runtime user is 65532, which could not then read it. **Pinned with `--checksum=sha256:…`, which is the opposite of the first draft's reasoning and the opposite is right.** That draft left it unpinned "so AWS's appends reach us"; BuildKit does not invalidate a remote `ADD` on content change, only on the URL, so unpinned actually means **frozen at whatever the bundle was on the first build**, silently, for the life of the layer cache. Pinning inverts the failure: when AWS appends a region the build breaks with a checksum mismatch, which is a visible prompt to review and update the pin. A broken build beats a stale trust store, and the bundle is 108 self-signed RDS roots that a reviewer can count. **This is the sibling project's post-merge hardening round, designed in at the start.**
- **A `-probe` flag rather than a separate probe binary.** The distroless gateway has no shell, so a `CMD-SHELL` health check cannot work, and something has to make the HTTP request. The sibling built a second binary and a second `apps/` entry; §2 (spec:38–43) enumerates four apps and a fifth would be a claim the spec does not make. `./gateway -probe` performs one `GET http://127.0.0.1:$PORT/health` with a 3-second timeout and exits 0 or 1. Same flag on the indexer against `$PROBE_PORT`. Twelve lines each, no new dependency, and the health check is `["CMD", "/gateway", "-probe"]`.
- **The image build context is the repository root**, `-f infra/<name>.Dockerfile .`, matching the sibling and matching what a Go module build needs. `infra/.dockerignore` excludes `.git`, `bin/`, `docs/`, `assets/`, `.superpowers/` and `node_modules/`.
- **`SCRATCH_DIR=/scratch`, `HOME=/scratch`.** The job trees and the go caches live under one directory the deployment can make the only writable path. **The first draft's reason for `HOME` was false and is worth correcting rather than deleting:** it claimed git would otherwise inherit no `HOME`, but `clone.Run` sets `HOME` itself, last, to the clone's parent (`clone.go:86`), and the compiler's comes from `Policy.Env()` (`policy.go:91`) — so the image's value reaches **neither** subprocess. What it does reach is the indexer process itself and anything else that ever runs in the container, and pointing that at the one writable path rather than at a non-existent `/home/nonroot` under a read-only root filesystem is still worth doing. A defensible setting with an indefensible reason is exactly the shape rule 4 exists to catch.

**Interfaces:**
- Produces in `metrics`:
  - `codetrail_job_total{outcome}` — `outcome` ∈ `{done, retried, failed}`, `failed` meaning terminal
  - `codetrail_job_seconds{outcome}` — histogram, exponential buckets from 1s (a job is minutes, not milliseconds)
  - `codetrail_admission_total{outcome}` — `outcome` ∈ `{accepted, rejected}`
  - `codetrail_admission_rejected_total{rule}` — `rule` ∈ `{form, scheme, host}`, exactly `admit.Rule`'s vocabulary

  - `codetrail_datastore_info{postgres, pgvector}` — gauge set to 1
  - `func CountJob(outcome string, d time.Duration)`, `func CountAdmission(accepted bool, rule string)`, `func CountEvicted(n int)`, `func SetDatastoreInfo(postgres, pgvector string)`
  - `JobOutcomes`, `AdmissionRules` — exported vocabularies, so a test can pin the label set against `admit`'s constants the way `GraphProvenances` is pinned against `models.Provenances`
- Produces in `health`:
  - `type Readiness struct { … }`, `func NewReadiness(log zerolog.Logger, ping func(context.Context) error) *Readiness`, `func (r *Readiness) Ready() bool`
- Produces in the indexer: an `echo.Echo` on `PROBE_PORT` (default `9090`) serving `/health`, `/ready`, `/metrics` through the existing `health.Register`.

**Decisions, with their reasoning:**

- **Both processes share one registry, and giving the indexer `/metrics` therefore publishes every gateway instrument at zero.** This is the decision with the largest blast radius in the task and it is not obvious from any one file. `metrics.go` registers all ten instruments with `promauto` on the **default** registerer at package init, and `init()` (`metrics.go:130–146`) materialises every label combination so that `rate()` has a series to work with before the first request. Both binaries import the package. So the moment `promhttp.Handler()` is mounted on the indexer, the indexer exports `codetrail_score_floor 0`, `codetrail_score_floor_calibrated 0`, `codetrail_answer_total{...} 0` and the rest — permanently, because only the gateway calls `SetFloor` (`main.go:199`) and `CountAnswer`. Two consequences, both of which are rules rather than notes:
  - **Every alert over a process-specific *gauge* must be scoped by `service`.** An unaggregated `codetrail_score_floor_calibrated == 0` matches the indexer's zero for ever and would keep a warning firing after P6 calibrates the floor — the exact "edited wrongly by an unrelated phase" failure the smoke test's invariant exists to avoid. Task 3's `ScoreFloorUncalibrated` carries `{service="gateway"}` for this reason. `codetrail_ready` needs no scope because both processes genuinely set it. **P7 adds five more gateway-only instruments and inherits this rule**, which is why it is written here rather than inside one alert's comment.
  - **Every alert over a *counter* is safe unscoped**, because the other process contributes a constant zero and `rate()` of a constant is zero. The ratio rules in Task 3 are therefore deliberately unscoped, and that is a decision, not an omission.
  The alternative — a private `prometheus.Registry` per binary — is a larger change to a package two other in-flight plans are editing, and it would buy nothing that scoping a gauge does not. Recorded as considered and refused.
- **Two admission counters, not one with a `rule` label.** `metrics.go:148–151` already states the reason for exactly this shape in the `answers`/`refusals` pair: the reason is only defined for one of the outcomes, and *"a label that is empty two thirds of the time is a label nobody can group by"*. Copying the shape rather than inventing a new one is also what lets §11's ratio alert have a denominator at all — "admission rejections by reason" (spec:273) gives a numerator and no denominator, and a rejection rate needs both.
- **Admission is counted in the gateway only.** Both binaries check (`apps/gateway/internal/handler/handler.go:146`, `apps/indexer/cmd/main.go:365`), and counting both double-counts every submission. The gateway's check is the one that becomes a `400` a user sees (spec:258); the indexer's re-check failing is a *job* failure with a reason and belongs to `codetrail_job_total`. Say so in the comment, because the next reader will otherwise "fix" the asymmetry.
- **`codetrail_job_seconds` is labelled by outcome.** Three outcomes times fourteen buckets is forty-two series, which is nothing, and *"how long does a failure take"* is a different and more useful question than *"how long does a job take"* — a job that fails at the deadline and one that fails at admission are the same counter and very different histograms.
- **`codetrail_evicted_total` counts rows, from `Evict`'s return value** (`packages/shared/store/evict.go:47`). Not one per sweep: §11 says "evictions" and a sweep that removed forty repositories and one that removed none are the same event and very different facts.
- **`codetrail_datastore_info` carries version strings as labels, against `metrics.go:2–3`'s own rule, and the exception is argued rather than assumed.** That rule closes labels to fixed vocabularies and names the things it is written against: a repo path, a file path, a symbol name, a question — all user-controlled and unbounded. A server version is bounded by the *database*, produces exactly one series per running deployment, and changes only when somebody upgrades. It exists because the pgvector version differs between compose and RDS and the honest response to that is to make it visible rather than to claim parity. This is the standard `*_info` shape; it is recorded as a deliberate deviation.
- **`readiness` moves into `packages/shared/health` rather than being copied into the indexer.** `apps/gateway/cmd/main.go:41–83` is the whole implementation, including the cache TTL that keeps a struggling database from being probed hardest when it can least answer, and the seeded-true construction that stops an unset gauge alerting on every start. A second copy in the indexer would agree on the day it was written. This is `chunk.Decl`'s lesson from P4, applied to a second pair.
- **The indexer's probe server is not on `PORT`.** `PORT` is the gateway's (`main.go:299`) and the two run in the same compose network; a shared name would make a copy-pasted task definition serve the wrong thing on the right port. `PROBE_PORT`, default 9090.
- **The indexer's `/ready` pings Postgres and nothing else.** It has no other dependency it can lose after boot: the embedder is probed once at boot and a job's embed failure is a job failure, not a readiness failure, and the go toolchain's absence is a *downgrade* by design (`graph.go:241–250`) and must never make a worker unready.
- **The probe server shuts down with the worker.** It is started before `ix.run(ctx)` and shut down after it returns, so a draining indexer stops answering `/health` and ECS replaces it instead of waiting.

### Task 3: The alert rules, and proving the conjuncts are load-bearing

**Files:**
- Create: `infra/prometheus/prometheus.compose.yml`, `infra/prometheus/prometheus.aws.yml`, `infra/prometheus/alerts.yml`, `infra/prometheus/alerts_test.yml`
- Modify: `infra/docker-compose.yml` — a `prometheus` service behind `--profile obs`
- Modify: `Makefile` — `alerts-test`
- Modify: `.github/workflows/ci.yml` — `promtool check` and `promtool test`

**Decisions, with their reasoning:**

- **The rule file is shared between compose and the cloud; the scrape file is not, and the difference decides what two alerts mean.** One `alerts.yml`, mounted locally and baked into the Prometheus task definition — a second copy would drift invisibly until an alert that fires locally does not fire in production. But discovery cannot be shared: compose has fixed container names and uses `static_configs`, while the cloud has tasks with rotating IPs and must use `dns_sd_configs` over the Cloud Map names. So there are **two scrape files** (`prometheus.compose.yml`, `prometheus.aws.yml`) with one `rule_files` entry between them, and each carries `labels: { service: … }` because `GatewayDown`, `IndexerDown` and `ScoreFloorUncalibrated` all select on it.
  **This is not a detail — it changes what "the indexer is parked" looks like.** Under `static_configs` a parked indexer keeps its target, `up` goes to 0, and `IndexerDown` pages critical for as long as the cheapest operating mode in the cost section is running. Under `dns_sd_configs` the target vanishes and `up` is *absent*, so `up == 0` cannot match — which is the behaviour that mode wants, and which also means `up == 0` cannot detect "no tasks at all" in the cloud. Both directions need saying, so the rules ship as a pair: `IndexerDown` (`up == 0`: scraped and not answering) and `IndexerAbsent` (`absent(up{…})`: nothing to scrape), the second of which is the one that fires in the cloud and is the one an operator silences while parked.
- **Every ratio rule is silent on an idle system, and this is a property of the design rather than of the thresholds.** `metrics.go:130–146` materialises every label combination at init, so an idle deployment reports `0` for numerator and denominator alike; `0/0` is `NaN`, and `NaN > threshold` is false in PromQL. So no ratio rule can alert on no data even before its conjunct is considered — the conjunct's job is the *thin*-data case (one event in an empty window), not the *no*-data case. Worth writing down because it is the reason the conjuncts can be set at genuinely small sample sizes without a divide-by-zero guard, and because a reader who does not know it will eventually add one back.
- **`promtool test rules` is this task's equivalent of mutation testing.** For every ratio rule it feeds a series at exactly the sample size the conjunct must hold back, asserts no alert, then adds one sample and asserts the alert. That converts "the conjunct is there" into "the conjunct decides the outcome", which is the difference between a rule and a decoration.
- **Minimum traffic is written as `N / <window seconds>`, never as a decimal.** `> 20 / 300` says "twenty answers in five minutes" to a reader; `> 0.0667` does not. This is the sibling's convention and the reason for it is legibility at 3am.
- **Each `N` is chosen so the events that would otherwise fire cannot clear the threshold on their own**, and the arithmetic is written into the comment. Anything else is a number that looks measured and is not.
- **Alertmanager is not deployed and the plan says so.** These rules evaluate and are visible in Prometheus; nothing pages anyone. Claiming otherwise would be the kind of thing this repository's README exists to refuse.

Nothing in this task creates a service. It creates the file layout, the variables, the network, the security groups, and — the point of the task — the **policy suite**, so that no Terraform in this phase ever lands without an assertion over it.

**Decisions, with their reasoning:**

- **No data source calls the AWS API.** This is the decision that makes every later assertion run on a laptop. The sibling stack's `data "aws_availability_zones"` is the single thing that forces credentials at plan time; here availability zones are `var.azs`, defaulting to `["us-east-1a", "us-east-1b"]`, with a `validation` block requiring exactly two. The cost is one variable an operator must set when changing region, and it is written into the variable's description. `data "aws_iam_policy_document"` stays: the provider renders it locally with no API call.
- **The provider sets `skip_credentials_validation`, `skip_requesting_account_id`, `skip_region_validation` and `skip_metadata_api_check`.** They suppress *configure-time* validation calls only; `apply` is unaffected. They are unconditional rather than behind a variable, because a plan that only validates offline when someone remembers to set a flag is a plan nobody validates offline.
- **The backend is a partial S3 config**, supplied at `init`. `backend.hcl.example` is committed; `backend.hcl` is ignored. `terraform init -backend=false` is what CI runs **for `validate` — and it is NOT enough for `plan`, which answers "Backend initialization required". Measured. `offline_plan.sh` writes a git-ignored local-backend override for the offline plan; the committed configuration still declares the real S3 backend.**
- **The state bucket holds the database password in cleartext, so its own requirements are written down here rather than left to whoever runs `init`.** State contains `aws_db_instance.password` and every `aws_secretsmanager_secret_version`. `backend.hcl.example` and the Terraform README therefore require: default encryption on (SSE-S3 at minimum, KMS preferred), **versioning on** — because a corrupted or truncated state is otherwise unrecoverable and the recovery is not "re-run apply" — a **public access block** on all four settings, and a bucket policy denying non-TLS requests. The bucket is not created by this stack (it must exist before `init`), which is exactly why its requirements have to be stated somewhere a person will read.
- **The RDS master password is `var.db_password`, supplied by the deploy workflow from a GitHub Actions secret**, validated for a URI-safe charset because it is interpolated into the DSN. Not `random_password`: that would put the generated value in state anyway while adding a resource whose whole purpose is to be unpredictable, in a stack whose plan output this phase asserts over. The honest alternative is `manage_master_user_password = true`, which hands the password to RDS and Secrets Manager and keeps it out of Terraform state entirely — **it is the better design and it is not chosen here**, because reading the generated secret back to assemble the DSN needs a data source, and a data source is an API call, and an API call is what would make `terraform plan` — and therefore this phase's entire policy suite — account-required. Recorded in Open question 9 as the first thing to change once an account exists.
- **`alb_allowed_cidrs` has no default and its validation refuses an empty list.** The sibling learned this after merge; here it is the first variable in the file. Its description says in one sentence that this stack publishes an unauthenticated endpoint that clones stranger-supplied URLs (spec:145–149).
- **`secret_recovery_window_days` defaults to 0.** Secrets Manager schedules a deleted secret for recovery and refuses to recreate a name still pending deletion, so a non-zero window makes destroy/apply cycles fail until it elapses. Zero trades recoverability for repeatability, which is the right trade for a stack whose cheapest operating mode is `terraform destroy` — and the wrong one once it holds a key in use, which the description says.
- **The policy suite is Go, behind `//go:build tfplan`.** Go because the toolchain is already in CI and the suite then inherits this project's testing discipline; a build tag because it needs an artifact that a plain `go test ./...` cannot produce; **and it fails rather than skips when `tfplan.json` is absent**, because P2's review round found two suites that emptied a developer's database while printing `ok`. `go vet -tags=tfplan ./...` joins `ci.yml:36–37`'s treatment of the `ollama` tag so the suite cannot rot between runs.
- **The suite parses `tfplan.json` with `encoding/json`.** `terraform show -json` has a documented, versioned schema and the assertions need `planned_values.root_module.resources` and nothing else. A dependency to read one map is a dependency to review forever.

### Task 5: Compute — two services, two security groups, one load balancer

This is where §2's sentence becomes a resource.

**Files:**
- Create: `infra/terraform/ecs.tf`, `alb.tf`, `iam.tf`, `ecr.tf`
- Modify: `infra/terraform/network.tf` (the per-service security groups), `variables.tf`, `outputs.tf`

**Decisions, with their reasoning:**

- **Three security groups minimum, and the indexer's is not the gateway's.** `aws_security_group.alb` takes ingress from `var.alb_allowed_cidrs` on 80 and 443. `aws_security_group.gateway` takes ingress on the gateway port **from the ALB security group only**, and egress on tcp/443 (Secrets Manager, ECR, CloudWatch Logs — all of which a Fargate task reaches through its own ENI) plus tcp/5432 to the data security group plus DNS. `aws_security_group.indexer` takes **no ingress except the scrape port from the observability security group**, and egress on tcp/443 plus tcp/5432 plus DNS — and nothing else. The difference between the last two is the deployment boundary; a test asserts it by rule content.
- **The indexer's egress is enumerated, never `protocol = "-1"`.** A single `-1` rule to `0.0.0.0/0` is what every ECS example ships and it opens tcp/22, tcp/9418 (`git://`) and every UDP port. The clone is https (spec:105) and the type-check fetches nothing (`policy.go:92`). **Corrected: the legitimate set is 443, 5432, DNS *and 11434* — both binaries make one real round trip to the embedder at boot and `log.Fatal` when it fails, so the set written here would have been a stack that cannot start.** This does **not** constrain which hosts — see "What §2, §4 and §11 decide", clause 2 — and the comment beside the rule says so, because a comment claiming host restriction here would be the highest-risk line in the file.
- **DNS egress is to the VPC CIDR and to `169.254.169.253/32`.** With `0.0.0.0/0` egress the question never arises; with enumerated egress it does, and a task that cannot resolve `github.com` fails every clone with a DNS error that looks like a network outage. Both are needed because the resolver's address differs between the VPC `.2` address and the link-local Route 53 endpoint.
- **The indexer is never an ALB target and never gets a target group.** Asserted, because the failure is silent: adding one costs nothing at apply time and publishes the untrusted-input component (spec:41) to the internet.
- **ALB target group health check → `/ready`; ECS container health check → `/health`.** Clause 4 above, with its reasoning. Both asserted, because asserting one is how the other goes wrong.
- **`readonlyRootFilesystem = true` on both containers**, with a bind-mount volume at `/scratch` and a second at `/tmp`. `linuxParameters.capabilities.drop = ["ALL"]` and `initProcessEnabled = true` — the latter because the indexer forks `git` and `go` and an unreaped child in a container with pid 1 as the application is a zombie per job.
- **`ephemeral_storage` of 40 GiB on the indexer task, and unset on the gateway.** 20 GiB comes free and 21 GiB is the smallest value the field can be *set* to, so leaving it unset on the gateway is not the same as setting it to 20; `MAX_REPO_BYTES` is 256 MiB per clone, the go caches are measured at roughly 0.7 MB per job under the shipped policy, and the headroom is for concurrent leases and for a checkout that expands. The gateway writes nothing.
- **Neither task definition has a `task_role_arn`, and for the indexer that is a control rather than a default.** This is the hole the environment allowlist below cannot see, because it is not in the environment the allowlist inspects: when a task role exists, the ECS agent injects `AWS_CONTAINER_CREDENTIALS_RELATIVE_URI` into the container at **runtime**, and `169.254.170.2` becomes a working credential endpoint — link-local, so no security-group rule touches it — inside the process spec:41 calls the untrusted-input boundary. `clone.Run` appends to `os.Environ()` (`clone.go:81`), so it reaches `git` as well. Nothing in this codebase calls any AWS API, so the role would buy nothing and grant something. `task_role_arn = null` on both, asserted; the **execution** role is a different field, is held by the agent rather than by the container, and is what pulls the image and the secrets.
- **The indexer's task-definition environment is an allowlist and is asserted as a whole set.** Permitted names: `DATABASE_URL` (from `secrets`, never `environment`), `ALLOWED_HOSTS`, `SCRATCH_DIR`, `PROBE_PORT`, `HOME`, `EMBED_PROVIDER`, `EMBED_MODEL`, `OLLAMA_URL`, `TYPECHECK`, and the caps. **`TYPECHECK_GOPROXY` is absent**, so it defaults to `off` (`graph.go:286`); if it ever appears the assertion requires it to equal `off`. Any name outside the set fails the test — which is how `HTTPS_PROXY` gets caught, and `HTTPS_PROXY` is the one that reaches `git` (`clone.go:81`) even though it cannot reach the compiler.
- **`deployment_circuit_breaker` with `rollback = true` on every service — and it cannot save the *first* deployment.** See "Migrations and rollback", consequence 4 for what it does afterwards. The exception matters here: with no prior COMPLETED deployment there is nothing to roll back to, so a failing first deploy **stalls** rather than reverting, and the workflow sits until it is stopped by hand. That is a second, independent argument for waiting on Ollama before the two services that boot-or-die on it (`fromenv.go:78–96`): on a first apply the circuit breaker is not a safety net, it is a slower way to fail.
- **Images come from ECR, not GHCR.** This repository is **private**, GHCR packages inherit repository visibility, and a private GHCR image fails a Fargate pull with `CannotPullContainerError` while the circuit breaker rolls the apply back — which is exactly what the sibling project hit and then had to fix with a credentials secret whose IAM grant was scoped wrong. ECR is pulled by the execution role through IAM, so there is no registry credential at all and the whole class of bug does not exist. `var.image_registry` still allows GHCR, and when it is used the `registry-credentials` secret lives **inside the same `for_each` map** the IAM grant iterates, which is the specific mistake being designed out.
- **Tasks run in public subnets with `assign_public_ip = true`.** A NAT gateway is $0.045/hr — **$32.85/month** before data processing — for a stack whose whole compute is under $130, and a public IP per task is $3.65. The tradeoff is stated: the tasks have public addresses and are protected by their security groups rather than by the absence of a route. For the indexer that is close to right — its only ingress is the scrape port, from the scraper's security group.

- **What builds:** `images.yml`, on **`pull_request`** (build only, `push: false`), on push to `trunk`, and on `workflow_dispatch`, a matrix over the Dockerfiles in `infra/`. The pull-request trigger is not optional: it is the only thing that makes the Dockerfiles verifiable with no cloud account, and two Definition-of-Done items depend on it. Tagged with the **commit SHA always**, plus `trunk` and `latest` on the default branch only. The SHA is the only tag that cannot move under a running service; `latest` exists solely because `var.image_tag` defaults to it and a deploy that names `latest` is a deploy nobody can reproduce.
- **What pushes:** ECR, via OIDC. Not GHCR — this repository is private and a private GHCR image cannot be pulled by Fargate without a credentials secret, which is the failure the sibling shipped. Building on every pull request with `push: false` is what makes the Dockerfiles verifiable with no account; **pushing** is `[ACCOUNT-REQUIRED]`.
- **What deploys:** `deploy.yml`, `workflow_dispatch` **only**, with a required `image_tag` input and no default. There is deliberately no `push` trigger: merging to trunk builds images and never touches infrastructure. `environment: production` is the second gate — dispatch alone only proves the actor has repository write access — and the workflow README says in as many words that **an environment with no required reviewers is a label, not a gate**. `concurrency: deploy-production` with `cancel-in-progress: false` **and `queue: max`**. `cancel-in-progress: false` alone does *not* queue: GitHub allows one pending run per group by default, and a newly queued run **cancels** the pending one it finds — so dispatching three times would run the first and the third and silently discard the second. `queue: max` is what makes them wait, FIFO, up to 100. Verified against GitHub's concurrency documentation rather than assumed, because the first draft claimed queueing from `cancel-in-progress` alone.

Applying a saved plan means the change that lands is exactly the change that was reviewed.
- **`aws ecs wait services-stable` after apply.** `terraform apply` returns when ECS accepts a task definition, not when it runs. Without the wait, a crash-looping service is a green workflow. **Ollama is waited on first, alone**, then the gateway and indexer — because both of those boot-or-die on the embedder's round trip (`fromenv.go:78–96`) and a first deploy that starts them together would have the circuit breaker roll back a stack that was about to work. - **The smoke test is one script with two targets.** `infra/smoke.sh <base-url>` runs against `http://localhost:8080` in CI over compose, and against the ALB after a deploy. One script, so the thing that runs after a deploy is the thing CI has been running all along.

- [ ] **Step 1: Write the smoke test**

What it asserts, in order, and **why each one is more than a 200**:

1. `GET /health` → 200. The process is listening. Weakest assertion in the file and it is here to be the first thing that fails.
2. `GET /ready` → 200 **and** `GET /metrics` contains `codetrail_ready 1`. The endpoint and the gauge, because spec:270 makes the gauge the signal and an endpoint that answers 200 with the gauge at 0 is a wiring bug that nothing else sees.
3. `GET /metrics` carries **both** floor gauges and they agree: `codetrail_score_floor_calibrated 1` implies `codetrail_score_floor` is a real cosine in `(0,1]`, and `codetrail_score_floor_calibrated 0` implies it is the `-1` placeholder. **Asserted as an invariant over the pair, not as a snapshot of either.** The first draft of this step asserted `calibrated 0`, which was true when this plan was written and stops being true the moment P6 lands — a smoke test that has to be edited by an unrelated phase is a smoke test that will be edited wrongly. P6's own plan records that `scoreFloor()` has exactly that bug latent today — an operator's `ANSWER_SCORE_FLOOR` inherits `Calibrated` from the default — so this is a live failure mode, not a hypothetical.
4. `GET /metrics` contains `codetrail_datastore_info` with a `pgvector` label ≥ `0.5.0`, and with the exact version recorded in the run's output. 0.5.0 is the HNSW floor; the version is *printed* rather than merely bounded because the assertion's real job is to catch an RDS minor upgrade moving the extension under a running deployment — RDS tops out at 0.8.2 while compose runs 0.8.6, so "the same as dev" is never the expected answer and only the recorded number tells an operator what actually served a query.
5. `POST /api/repos {"remote":"https://gitlab.com/x/y"}` → 400 with `"rule":"host"`. **The allowlist was not widened by the deployment.** A negative assertion, and the only one that can catch an `ALLOWED_HOSTS` set to something permissive in a task definition nobody reads.
6. `POST /api/repos {"remote":"https://github.com/rs/zerolog","ref":"master"}`, then poll `GET /api/jobs/{id}` to `done` within a bounded wait. This is the whole untrusted path in one assertion: the indexer leased a job, cloned through the security group's 443 egress, resolved DNS, walked, chunked, embedded against Ollama, type-checked under the environment allowlist, and wrote. Nothing else exercises the egress rules at all.
7. `GET /api/repos/{repo}` and assert **`edges_resolved > 0`**. **This is the most valuable assertion in the file.** If the image shipped no Go toolchain, or shipped two, or `PATH` resolved a different one, the repository still indexes, every response is still 200, and every edge is silently syntactic — the exact downgrade `README.md:540` warns P8 about and the one thing no status code can reveal.
8. `POST /api/repos/{repo}/ask` and assert the response carries at least one citation whose `commit` equals the repository's `commit_sha`. A citation pointing at a different commit is the one failure mode that would make the product's first sentence false.
9. `GET /metrics` on the **indexer's** probe port contains `codetrail_job_total{outcome="done"}` greater than it was at step 6. Proves the metrics the alerts depend on actually moved, on a real job, in the deployed shape.

**Which of these can run against which target, because the honest answer is not "all nine against both".** The ALB routes `/api/*` to the gateway and makes the console the default action, but the gateway serves `/health`, `/ready` and `/metrics` at the **root** (`health.go:11–19`, mounted at `server.go:20`). So against the deployed URL those four paths reach the console's nginx, and with SPA fallback **step 1 would pass falsely** while steps 2–4 failed on content — the worst possible combination. The script therefore takes a `--target compose|deployed` mode and each mode asserts what it can actually see:

| Step | compose | deployed |
| --- | --- | --- |
| 1–2 liveness and readiness | `curl` the gateway directly | **`aws elbv2 describe-target-health`, requiring `State: healthy`** — the target group probes `/ready` (Task 5), so a healthy target *is* step 2's assertion, made continuously by AWS rather than once by curl |
| 3 floor-gauge invariant | `/metrics` | the gateway's boot log line via `aws logs filter-log-events` (`main.go:200–205` already logs the floor and whether it is calibrated) |
| 4 pgvector version | `/metrics` | the same boot log line, which Task 2 extends with the datastore versions for exactly this reason |
| 5–8 admission, index, `edges_resolved`, citations | `/api/*` | `/api/*` — **identical, and these are the assertions that matter** |
| 9 indexer job counter | the indexer's probe port | from Prometheus when `observability_enabled`, otherwise **printed as not asserted** and never silently skipped |

So the earlier draft's claim that this is "one script, so the thing that runs after a deploy is the thing CI has been running all along" was true of steps 5–8 and false of the rest. It is one script with a target-dependent subset, the subset is printed at the top of every run, and the four assertions that prove the deployment actually works — the allowlist was not widened, a stranger's repository indexed end to end, edges resolved, citations point at the indexed commit — are the ones that are identical in both modes. The alternative was a listener rule publishing `/health` and `/metrics` through the ALB, which the console assumption forbids for a good reason and which would trade a real exposure for a tidier table.

## Open questions

Nothing here is blocking. Each is something the spec does not settle, with the tradeoff and a recommendation, so a reviewer can disagree with a decision rather than discover it.

1. **The embedder is 42% of the bill and the code has two providers, one of which is a fake.** `packages/shared/embed/fromenv.go:45–69` accepts `ollama` or `fake`; both binaries refuse to boot without a working one. So a cloud deployment runs Ollama on CPU-only Fargate at ~$72/month whether anyone visits or not, and spec:230–232's *"a public demo costs nothing per visitor"* is true of the answering path and false of the deployment as a whole — every question is an embed.
   *Recommendation:* ship Ollama, cost it openly, and **do not add a provider in P8**. A hosted embedder is a code change with a hard constraint: `store.EmbeddingDim` is 768 and `store.CheckDim` refuses anything else (spec:94–97), so a candidate has to produce 768 dimensions natively or support dimension reduction — OpenAI's `text-embedding-3-small` with `dimensions=768` fits, and whether truncated embeddings retrieve as well is exactly the kind of question this project answers with an eval rather than an assumption. It belongs in a phase that can measure it against P6's harness.

2. **Both applications boot-or-die on the embedder, so service start order becomes a deployment concern the code does not express.** `fromenv.go:78–96` makes one real round trip at boot with a 30-second deadline; `apps/gateway/cmd/main.go:286–289` fatals on failure. On a first apply, ECS starts all services together, the gateway cannot reach an Ollama that is still loading its model, it exits, and the circuit breaker rolls back a stack that was about to work.
   *Recommendation:* wait on `ollama` alone before waiting on the others in `deploy.yml`, and bake the model into the Ollama image so its start is a load and not a download. This is a workflow-shaped fix for a code-shaped problem and it is worth naming as such: the alternative — a bounded retry around `embed.FromEnv` at boot — is three lines and would make the deployment order irrelevant, but it changes a boot contract this phase said it would not touch. Revisit when P7 adds a second provider and the boot path has to handle a rate limit anyway.

3. **The network layer cannot enforce the host allowlist, and two things that look like they could, cannot honestly.** An IP prefix list built from `api.github.com/meta` goes stale silently — GitHub's ranges change, and a stale entry is a clone that fails for a reason nobody can find. An egress proxy that terminates TLS is a second trust boundary and a place a stranger's `git` credentials would pass through.
   *Recommendation:* enumerate ports, never hosts, and say so in the comment beside the rule. §4 already states that host-allowlisting is *the* control and that there is no DNS-rebinding protection (spec:126–130); the deployment adding a control that half-works would make that paragraph misleading. Revisit if the corpus ever needs a forge whose ranges are stable and published.
   *P7's request, answered rather than deferred.* P7 asks P8 for a network-level egress allowlist on the **gateway's** task, and its case is genuinely stronger than the indexer's: the indexer's destination is chosen by a stranger's URL, while the gateway's is a constant already pinned in code at boot. It is still not a host a security group can name. What Task 5 delivers is the strongest thing at that layer — the gateway's egress is enumerated to 443, 5432 and DNS rather than `protocol = "-1"`, so an exfiltration path over any other port does not exist — and what it does not deliver is host restriction, which needs a TLS-terminating proxy this project refuses for the same reason it refuses one for the indexer. The difference between "cannot reach anything but 443" and "cannot reach anything but Anthropic" is real and is stated in the README rather than papered over.

4. **`/metrics` is unauthenticated on both services** (`health.go:19`), and P5's decision settles most of what to do about it.
   *Decided, because the console forced it:* the ALB publishes exactly two things — `/api/*` to the gateway and the console bundle — so `/health`, `/ready` and `/metrics` have **no listener rule** and are reachable only by the target group health check and by the scraper inside the VPC. That is stronger than the "leave it, the labels are closed" answer this question started with, and it costs nothing, because P5's console never requests those paths at runtime; only Vite's development proxy does. What remains open is the residual: the endpoints are still unauthenticated *within* the VPC, which matters only if something untrusted ever runs there — and the one component that handles untrusted input accepts nothing but a scrape from the scraper's own security group.
   *Revisit if* an operator ever wants Grafana outside the VPC, at which point the answer is a second, separately-scoped listener rather than widening this one.

5. **The job history sweep and eviction both run on a timer inside the indexer, so a parked indexer stops evicting.** `desired_count = 0` — the cheapest operating mode in the cost section — stops LRU eviction and job-history sweeping along with indexing.
   *Recommendation:* accept it and write it down. Both are bounded-growth mechanisms and nothing grows while nothing is being submitted; the corpus can only exceed `KEEP_REPOS` while an indexer is running, which is when the sweep runs. Revisit if a future phase moves eviction to the gateway or to a scheduled task.

6. **ARM64 Fargate is 20% cheaper and is not the default.** Roughly $25/month on this shape. It needs an arm64 Go toolchain in the indexer image and an arm64 build in `images.yml`, which means either QEMU — an emulated Go build, slow — or ARM runners, which are not free on a private repository.
   *Recommendation:* keep `linux/amd64` and expose `cpu_architecture` as a variable so the switch is one line plus one matrix entry. Measure the build time on QEMU before deciding; if it is minutes rather than tens of minutes, the saving is worth it.

7. **The stack has no backup that is not the remote it came from.** `skip_final_snapshot = true` and a one-day retention window on a `db.t4g.micro`.
   *Recommendation:* correct for this product and it should be stated rather than defaulted. Every row in the database is derived: repositories are re-indexed from their remotes, `RepoID = hash(remote, commit)` makes re-indexing converge, and spec:141–143 already treats the corpus as evictable. The one thing that is *not* derived is the `jobs` table's history, and spec:145–149 makes that explicitly disposable too. Revisit the moment anything user-authored is stored.

8. **The gateway's egress is as wide as the indexer's, and closing it costs about $29/month.** Clause 1's table is honest about this: both tasks need outbound 443 because a Fargate task pulls its image, reads its secrets and ships its logs through its own ENI, and there is no AWS-managed prefix list for ECR, Secrets Manager or CloudWatch Logs to scope that with.
   *Recommendation:* ship the honest version, and record the upgrade rather than half-doing it. Interface VPC endpoints for `ecr.api`, `ecr.dkr`, `secretsmanager` and `logs`, plus the free S3 *gateway* endpoint that ECR layer pulls actually use, at roughly $7.30/month each; the gateway's 443 then points at the endpoints' security group and not at the internet, and clause 1's egress row becomes a genuine difference — the indexer still needs the world, the gateway no longer does. It also answers P7's request at a granularity a security group can express. Behind `private_endpoints_enabled`, default `false`, with the policy assertion conditioned on it so the stronger claim is only asserted where it is true. Not built in P8 because it is $29/month for a stack whose cheapest honest mode is `terraform destroy`, and because an untested endpoint configuration is a first apply that fails at image pull.

9. **The RDS master password passes through Terraform state, and the fix would make this phase account-required.** `manage_master_user_password = true` hands generation and rotation to RDS and Secrets Manager and keeps the value out of state entirely — strictly better security, and the reason it is not chosen is not security but verification: reading the generated secret back to assemble the DSN needs a data source, a data source is an API call, and one API call turns `terraform plan`, `terraform show -json` and this phase's whole policy suite from "runs on every pull request" into "needs an account".
   *Recommendation:* keep `var.db_password` while there is no account, and make this the **first** change once there is one, together with the destroy-and-recreate cycle in Task 8. Record it in the account-required ledger so it is a scheduled improvement rather than a thing someone notices later. The mitigation meanwhile is the state bucket's own requirements in Task 4 — encryption, versioning, public-access block, TLS-only.

10. **Prometheus in AWS is a fourth service with no persistence and no Alertmanager.** ~$13/month for a task whose rules evaluate and whose graphs vanish on restart.
   *Recommendation:* ship it behind `observability_enabled`, defaulting to `false`, and run the same rule file locally under compose where it costs nothing. A dashboard nobody looks at is not worth $13/month; the rule file is worth having regardless, because it is the executable form of what §11 asked for and `promtool` proves it works with no account at all.

## What the spec leaves underspecified or in tension

Recorded so a reviewer sees them as findings rather than as choices made quietly.

- **§11 describes an observability surface the indexer has never had, and three of the five instrument families it names do not exist in code.** spec:269 says *"Prometheus on `/metrics`, `/health` for liveness and `/ready` for dependency health"* as a project-wide statement; the indexer runs no HTTP server at all, and `packages/shared/metrics/metrics.go` contains ten instruments of which **none** is job outcomes, job durations, admission rejections by reason, or evictions (spec:273–274). Three of the four are indexer-side, so the missing endpoint and the missing counters are the same gap seen twice. P3 recorded it, P4 recorded it again and declined to fix it. **Proposed resolution:** Task 2 adds the probe surface and the three families, and this is recorded in the README as P0-shaped work that arrived in P8 because that is the phase where §11 stopped being aspirational.
- **§8's "a public demo costs nothing per visitor" is true of the answering path and false of the deployment.** spec:230–232 argues extractive answering has zero marginal cost and works offline — which it does. But retrieval embeds the *question* on every request, `embed.FromEnv` has no zero-cost real provider, and the cheapest thing that satisfies it in AWS is a 2-vCPU Ollama at ~$72/month whether anyone visits or not. The sentence is about the LLM and reads as being about the deployment. **Proposed resolution:** leave the spec alone and let the README's cost table say what the deployed shape costs, with the sentence quoted and the distinction drawn. A spec edit would be rewriting history to match an outcome.
- **§2 makes the indexer the untrusted-input boundary and §11 requires it to be scraped, which means it must listen.** spec:41 and spec:269 are in quiet tension: the component with no ingress is the component that must serve `/metrics`. The tension is small and real, and the resolution is that the listener exists on a port with no route from outside the VPC and one security-group rule from the scraper. It is worth writing down because the obvious "fix" — pushing metrics out instead — would give the untrusted-input component a *new outbound destination*, which is the wrong direction.
- **§4's caps bound a job and not an arrival rate, on an endpoint with no auth.** spec:109–110 and spec:145–149 together describe a public endpoint that will `git clone` a stranger's URL, with per-job byte, file and time caps and no bound on how many jobs. In a deployment that is a cost and availability question the spec does not answer. **Proposed resolution:** make it the operator's explicit choice through `alb_allowed_cidrs` with no default, and say in the README that `["0.0.0.0/0"]` here means an unauthenticated repository-cloning endpoint on the public internet. A rate limit belongs in the gateway where it can name its own rule (spec:258); adding one at the edge would make the API's behaviour depend on which door the request came through.
- **§13 gives P8 three words and puts it last.** spec:304 — *"Terraform, CD, deploy"* — is the whole specification for this phase. Everything about the compute shape, the cloud, the image layout, the health-check split, the alert thresholds and the secret delivery is a decision this plan made; the open questions say which ones a reviewer is most likely to want changed.
- **The spec never says what `codetrail_ready` should do in the indexer**, which has no request path to protect. §11 defines readiness as dependency health (spec:269–271) and the indexer's only post-boot dependency is Postgres. **Proposed resolution:** ping Postgres and nothing else, and specifically **do not** make a missing Go toolchain unready — `graph.go:241–250` makes that a downgrade by design, and an alert on it is `TypecheckHasNoToolchain`, not readiness. A test pins it, because "the indexer cannot type-check, mark it unready" is the change a reasonable reviewer would ask for and it would turn a documented degradation into an outage.
- **`0006_drop_repo_status.sql` is a destructive migration in a system that migrates at boot and rolls back by task definition.** It is safe because nothing ever read the column, and its own comment says so — but it establishes a precedent that a future destructive migration would follow into a rollback that cannot work. **Proposed resolution:** the expand-only rule in "Migrations and rollback", enforced by `make migrations-lint` in CI rather than written as a convention — `0006` itself takes the first exemption marker, so the rule ships having already been applied to the one file that violates it.

## Where this plan was wrong

Beyond the counterfactual corrections above.

1. **`infra/.dockerignore` would have been silently ignored.** With the context
   at the repository root, BuildKit reads `<dockerfile>.dockerignore` or the
   root `.dockerignore`, never `infra/.dockerignore`. Measured: `docs/` and
   `assets/` were still in the context. The file is at the root and
   `image_test.sh` asserts the exclusion by name.
2. **`terraform init -backend=false` and `terraform plan` are incompatible.**
   The plan says `-backend=false` "is what CI runs" *and* that CI runs
   `plan -out`. With a backend block declared, plan answers "Backend
   initialization required". `offline_plan.sh` writes a git-ignored
   local-backend override.
3. **`terraform show -json` is not byte-stable across two plans**, in three
   places: `timestamp`, `relevant_attributes` (reordered), and
   `configuration.*.expressions.*.references` — three consecutive plans gave
   three orders for one ingress block. The last is inside a section the
   assertions read, so it is sorted rather than dropped.
4. **`container_definitions` is unknown at plan time whenever anything inside
   it references a resource attribute**, which would have left the environment
   allowlist, the user, the read-only root filesystem, the capabilities and the
   health checks with nothing to assert over. Two fixes: the image reference is
   built from `var.image_registry` rather than from
   `aws_ecr_repository.repository_url` (the same trade the plan already made for
   availability zones), and the secret ARN — which AWS requires in full, with
   the random suffix, so it cannot be built from a variable — is handled by
   `outputs.container_shape`, which is `local.container` with that one field
   replaced by the secret's name.
5. **The enumerated egress had no port for the embedder.** The plan says the
   indexer's egress is "443 plus 5432 plus DNS — and nothing else", and both
   binaries make one real round trip to Ollama at boot and `log.Fatal` when it
   fails. 11434 is now in the set and in the assertion.
6. **`TestTheIndexersEgressPortsAreExactly443And53` contradicts its own task's
   decision text**, which says 443 *plus 5432* plus DNS. Renamed to
   `…443And5432AndDNS` and now covers 11434 as well.
7. **An inline egress naming the data security group and an inline ingress
   naming the app groups are a dependency cycle.** The port is narrowed on the
   egress side by CIDR, and who may connect is decided on the ingress side.
8. **Terraform emits no `lifecycle` block anywhere in the plan JSON**, so a
   precondition cannot be asserted from the artifact. The assertion reads the
   HCL and says so, rather than checking nothing.
9. **The plan's configuration section does not expand a local**, so
   `secret_string = local.database_url` records one reference and the DSN's
   shape becomes invisible. The DSN is written out at the secret version.
10. **`queue: max` is correct and `actionlint` 1.7.12 rejects it.** Verified
    against GitHub's workflow-syntax reference: the key exists, takes `single`
    or `max`, and `max` allows up to 100 pending runs. `.github/actionlint.yaml`
    carries the one ignore with that citation.
11. **The instrument count carried forward was right and the plan's own body was
    inconsistent.** Three indexer instruments, not seven — the README was right
    and P4's prose was not, exactly as this plan said.
